### 各测试文件的实际含义（源码事实）

- `test_detection.py` 直接调用 `services/detection.py` 的函数，**不经 HTTP 层**；其中多处通过 `create_log()` 造数据（`:30,49,70,89,107,117`）。
- `test_integration.py` 使用 `TestClient` 走完整 HTTP 栈；类 `TestAuthIntegration`、`TestLogsIntegration`、`TestDetectionIntegration`、`TestAlertsIntegration`、`TestStatsIntegration`、`TestDeduplication`、`TestSSEPublish`、`TestEndToEnd`。
- `TestSSEPublish` 只验证 `_publish_alert_event` 调用了 `publish("alerts", ...)`，**不验证 SSE 端点本身**（`GET /api/notifications/stream` 无任何测试）。

## 19.3 实测运行结果（本次审计环境）

| 命令 | 结果 |
|---|---|
| `python -m pytest tests/test_health.py tests/test_security.py -q` | **3 passed**（0.65s） |
| `python -m pytest tests/test_alert_stats.py -q` | **4 passed**（0.83s） |
| `python -m pytest tests/test_integration.py -q -o faulthandler_timeout=45` | **29 passed**（5.83s） |
| `python -m pytest tests/test_detection.py -q -o faulthandler_timeout=20` | **卡死**：`Timeout (0:00:20)!` |
| `python -m pytest tests/ -q`（全量） | **超过 300 秒未结束**（被超时终止） |

**卡死根因（实测栈证据）**：
```text
tests/test_detection.py:30
  → app/services/logs.py:58  detect_anomaly_for_log.delay(log.id)
  → celery/app/task.py:444 delay → app/base.py:798 send_task
  → celery/backends/redis.py:373 on_task_call → consume_from → _reconnect_pubsub
  → kombu/utils/functional.py:318 retry_over_time
  → redis/connection.py:615 _connect   ← 无限重试
```
该机的 Docker 守护进程未运行，Redis(8880) 不可达；由于 Celery 把 Redis 同时配置为 **result backend**（`tasks/__init__.py:7`），发布任务时会尝试启动结果消费端并无限重连，因而测试无法失败退出而是挂住。

**结论**：`AGENTS.md` 中「全部 42 个测试可离线运行」的说法**与实测不符**——36 个用例可离线通过，6 个检测用例会挂死。

## 19.4 覆盖情况评价

### 有测试覆盖的部分

| 能力 | 覆盖程度 |
|---|---|
| 认证（登录、注册、me、鉴权失败） | 较好（含错误分支与重名分支） |
| 两条检测规则与阈值分档 | 较好（medium/high 边界都有用例） |
| 告警去重 | 较好（pending / resolved / 不同类型三种情形） |
| 日志上报与查询接口 | 中等（API Key 三种情形、鉴权、结构；无筛选组合与分页边界用例） |
| 告警接口 | 中等（列表/详情/更新/404；无清空接口用例） |
| 告警统计接口 | 中等（结构与趋势长度；`days` 越界 400 无用例） |
| 端到端主链路 | 1 个用例覆盖登录→上报→检测→告警→处置→统计 |

### 测试设计层面的问题

| # | 问题 | 依据 | 影响 |
|---|---|---|---|
| T1 | 检测测试未屏蔽 Celery 投递，导致无 Redis 时挂死 | `test_detection.py:30` 等 vs `test_integration.py:103-106` 的 autouse patch | 本地/CI 无法稳定跑完测试 |
| T2 | 屏蔽方式为「点对点 patch」而非全局配置 | 同上 | 新增测试容易再次踩坑（应放到 `conftest.py` 或设 `task_always_eager`） |
| T3 | 测试用 SQLite，生产用 MySQL | `conftest.py:16`、`docker-compose.yml:5` | 外键级联、DDL 严格模式、`DATETIME` 时区等行为差异无法在测试中暴露（例如 `DELETE /api/logs` 的外键冲突、迁移在非空表上的失败都不会被发现） |
| T4 | 无覆盖率度量 | 无 `pytest-cov` | 无法量化回归风险，也让「新增测试」缺少目标 |
| T5 | 无 CI | 无 CI 配置 | 测试是否被执行完全依赖开发者自觉 |
| T6 | 无前端/客户端测试 | 两端均无测试设施 | 已有的前端缺陷（如 SSE 重连计数被重置、401 吞提示）本可被测试捕获 |
| T7 | 端到端用例与 service 直测混用同一批 fixture，但断言偏「结构存在」 | 例如 `test_stats_empty_data` 只断言长度与类型 | 对数值正确性的校验较弱 |
