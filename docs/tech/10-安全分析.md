# 20. 安全分析

> 本章只列出**有源码证据**的问题，并标注严重程度。分级依据：可利用性、影响面、是否需前置条件。
> 说明：本项目是**安全审计平台**，其自身安全性尤为关键——若平台被攻破，攻击者可获得全校登录行为数据，甚至通过伪造日志污染检测结果。

## 20.1 认证与凭据

### SEC-01｜JWT 通过 URL query 传递（**High**）

| 项 | 内容 |
|---|---|
| 文件/行为 | `api/notifications.py:33` 用 `token: str = Query(...)` 接收 JWT；两端同样把 token 拼在 URL：`frontend/src/stores/notification.js:20`、`flutter_app/lib/providers/notification_provider.dart:33-35` |
| 风险 | token 进入 Nginx/代理访问日志、浏览器历史、Referer 头；默认有效期 1440 分钟且**无吊销机制**，泄露即可重放 |
| 影响 | 攻击者获得管理员权限（`nginx.conf:12-25` 未关闭该路径的访问日志） |
| 已知约束 | 浏览器 `EventSource` 无法自定义请求头，属权衡设计（`AGENTS.md` 亦有说明） |
| 建议 | ① 为 SSE 签发**短时效、单次使用**的 ticket（用 JWT 换 ticket 后再建流）；② 或改用手写 SSE（`fetch` + `ReadableStream`）以便使用 `Authorization` 头；③ 至少在 Nginx 中对该路径关闭 `access_log`，并缩短 SSE token 有效期 |

### SEC-02｜默认密钥未强制替换（**High**，配置类 —— 已修复 2026-09-16）

> **修复状态**：已修复。`core/config.py:assert_secure_config()` 在启动期检测占位值——`ENVIRONMENT=production` 时**拒绝启动**，开发环境打印强警告；`main.py` 与 `tasks/__init__.py` 均会执行；`describe_effective_config()` 打印的有效配置摘要已抹除凭据。回归用例：`tests/test_config.py`。

| 项 | 内容 |
|---|---|
| 文件/行为 | `SECRET_KEY` 默认 `your-secret-key-change-in-production`（`core/config.py:13`），compose 值为 `change-me-to-a-random-secret-in-production`（`docker-compose.yml:50`）；`API_KEY` 默认 `dev-api-key-change-in-production`（`core/config.py:16`） |
| 风险 | 使用默认 `SECRET_KEY` ⇒ 任何人可自签 JWT 冒充管理员（算法 HS256，`core/security.py:10`）；使用默认 `API_KEY` ⇒ 任何人可伪造日志上报，**污染检测结果、制造虚假告警或掩盖真实攻击** |
| 影响 | 完全绕过认证 / 污染安全数据 |
| 建议 | 启动时校验（`SECRET_KEY`/`API_KEY` 命中已知占位值时拒绝启动或输出醒目警告）；compose 改用 `env_file` + 必填校验；文档明确列为部署前置项 |

### SEC-03｜真实 SMTP 凭据存放于工作区（**Medium**）

| 项 | 内容 |
|---|---|
| 文件/行为 | `backend/.env` 存在且含真实 SMTP 凭据（键名与存在性已核实，值未读取/未记录） |
| 缓解现状 | 已被 `.gitignore:18` 忽略（实测 `git check-ignore` 命中）；`backend/.dockerignore:6` 亦排除 `.env`，不会进镜像 |
| 风险 | 本机文件泄露、截图/备份外传即凭据泄露 |
| 建议 | 继续不提交；使用应用专用授权码并定期轮换；文档与截图一律使用 `<YOUR_SMTP_PASSWORD>` 占位 |

### SEC-04｜认证失败原因可区分但响应含业务提示（**Low/Info**）

`api/auth.py:22-25` 把 `AuthenticationError` 的文案直接作为 `detail` 返回（`"用户名或密码错误"` vs `"用户已被禁用"`）。当前「用户名不存在」与「密码错误」使用同一文案（`services/auth.py:18`），**不存在用户名枚举**；但禁用状态可被区分，属可接受的信息量。

## 20.2 权限控制与边界

### SEC-05｜无 RBAC，`role` 字段形同虚设（**Medium**）

| 项 | 内容 |
|---|---|
| 文件/行为 | `users.role` 默认 `admin`（`models/user.py:19`）；全项目**没有任何依据 `role` 的鉴权分支**（实测 grep），唯一的读取点是邮件收件人筛选（`tasks/email.py:22`） |
| 风险 | 无法实现「只读审计员」「仅处理告警」等最小权限角色；`POST /api/auth/register` 允许**任意已登录用户**创建新管理员（`api/auth.py:28-39`） |
| 建议 | 引入角色枚举与依赖（如 `require_role("admin")`）；注册接口限制为特定角色 |

### SEC-06｜销毁性接口无二次确认、无审计（**Medium —— 已修复 2026-09-16**）

> **修复状态**：已修复。两个 DELETE 端点要求 `confirm=true`（缺失返回 **409**），执行**软删除**（写 `deleted_at`，数据保留），并写入 `audit_logs`；新增 `GET /api/audit-logs` 查询审计记录。回归用例：`tests/test_governance.py`。

| 项 | 内容 |
|---|---|
| 文件/行为 | `DELETE /api/logs`（`api/logs.py:50-58`，清空全表）、`DELETE /api/alerts?scope=all`（`api/alerts.py:83-96`） |
| 风险 | 任何持有有效 JWT 的人可一键清除全部日志/告警（**销毁证据**）；无软删除、无操作日志、无角色限制；前端虽有确认框，但 API 层可直接调用 |
| 影响 | 安全审计平台丢失审计数据，且无痕迹 |
| 建议 | 后端加显式确认参数/二次校验；改为软删除（`deleted_at`）；记录操作者与数量到审计日志；按角色限制 |

### SEC-07｜无登录速率限制与账号锁定（**Medium —— 已部分修复 2026-09-16**）

> **修复状态**：部分修复。新增 `core/ratelimit.py`（Redis 固定窗口计数，Redis 不可用时 fail-open 并熔断 30s）并接入登录：同一「用户名 + 来源 IP」窗口内失败达 `LOGIN_MAX_FAILURES`（默认 5）返回 **429 + Retry-After**；`scripts/seed.py` 创建的默认管理员带 `must_change_password=True`，未改密时其它接口返回 403。**仍未做**：账号锁定、口令复杂度规则、口令历史。回归用例：`tests/test_governance.py`。

`POST /api/auth/login`（`api/auth.py:14-25`）无任何限流/失败计数；结合默认管理员口令 `admin/admin123`（`scripts/seed.py:29`、`README.md:33` 公开写明）与无密码强度校验的注册接口，在线爆破成本极低。

**建议**：按 IP + 账号维度限流（Redis 计数即可，项目已有 Redis）；首次登录强制改密；禁止在文档/界面公开默认口令。

## 20.3 注入类风险（结论：未发现可利用问题）

| 类别 | 结论 | 依据 |
|---|---|---|
| SQL 注入 | **未发现** | 后端全部走 SQLAlchemy ORM（实测 grep 无 `text()`/裸 `execute()`）；`monitored-app/app.py:42`、`seed.py:29` 使用参数化占位符 `?` |
| 命令注入 | **未发现** | 实测 grep 无 `subprocess`/`os.system`/`shell=True` |
| 不安全反序列化 | **未发现** | 无 `pickle`/`eval`/`exec`/`yaml.load`（实测 grep） |
| SSTI（服务端模板注入） | **未发现** | `monitored-app` 模板仅使用 `{{ username }}` 变量（`templates/welcome.html:16`、`index.html:56`），Jinja 对 `.html` 默认开启自动转义 |
| XSS | **未发现明确问题** | Vue 默认转义插值；Flask 模板转义开启。**但**前端把 token 存于 `localStorage`（`api/index.js:10`），一旦出现 XSS 即可窃取 token —— 属纵深防御风险而非现存漏洞 |
| 路径穿越 / 文件上传 | **不适用** | 无文件上传、无文件路径类接口（`python-multipart` 虽被安装但无使用点） |

## 20.4 跨域与浏览器侧

### SEC-08｜CORS 通配 + 允许凭证（**Medium**）

| 项 | 内容 |
|---|---|
| 文件/行为 | `main.py:21-27`：`allow_origins=["*"]`、`allow_credentials=True`、方法与头全放开 |
| 风险 | Starlette 在 `allow_credentials=True` 且 `allow_origins=["*"]` 时会**回显请求的 Origin**，等价于允许任意站点带凭证发起跨域请求；若将来把 token 改存 Cookie，将直接构成 CSRF 面 |
| 影响 | 当前 token 在 `localStorage`，恶意站点无法直接读取，风险受限；但配置本身不应用于生产 |
| 建议 | 收敛为白名单域名；如无跨域需求则移除该中间件 |

### SEC-09｜CSRF（**Low**）

当前鉴权凭据在 `Authorization` 头 / `X-API-Key` 头（非 Cookie），浏览器不会自动携带，故**不构成经典 CSRF**。风险仅在前端把凭据迁移到 Cookie 后成立。

## 20.8 安全结论汇总

| 级别 | 条目 |
|---|---|
| **Critical** | 无（未发现可立即导致未授权数据访问或远程执行的现存缺陷） |
| **High** | SEC-01 JWT 走 URL query；SEC-02 默认密钥未强制替换；输入校验里的 `days` 无上限（DoS） |
| **Medium** | SEC-03 真实 SMTP 凭据在本地文件；SEC-05 无 RBAC；SEC-06 销毁性接口无确认/审计；SEC-07 无登录限流；SEC-08 CORS 通配 + 凭证；SEC-09/输入校验（`login_status`/`status`/注册）；SEC-12 平台自身无审计日志；SEC-15 仿真器 debug 模式 |
| **Low / Info** | SEC-04、SEC-10、SEC-11、SEC-13、SEC-14、SEC-16 ~ SEC-19 |

> **未确认项**：本项目未做依赖漏洞扫描（无 `pip-audit`/`npm audit` 记录），因此**不声称存在已知 CVE 漏洞**；依赖版本（如 `fastapi 0.104.1`、`python-jose 3.3.0`、`axios 1.18.1`）是否需要安全升级，需执行扫描工具后才能定论。同理，「SSE 连接池耗尽」「外键删除失败」等结论均为**静态分析**，未在真实 MySQL/网络环境下复现。

### 平台定位带来的额外建议

作为安全审计平台，建议补齐以下「自身安全基线」，其价值高于继续增加检测规则：

1. **操作审计日志**（谁、何时、做了什么、影响多少行数据）——当前完全缺失，却监控着别人的登录行为；
2. **数据留存策略**：日志不加密、无归档、可一键清空；
3. **最小权限**：`role` 已存在但未使用；
4. **密钥治理**：默认值检查 + 轮换机制；
5. **上线前配置收敛**：CORS 白名单、关闭 `debug`、移除示例口令。
