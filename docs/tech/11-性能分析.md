# 21. 性能分析

> 本章严格区分：**已确认问题**（有实测证据或源码确定行为）、**潜在风险**（由结构推导，未压测）、**未确认**（需基准测试才能定论）。
> 本次审计**未做任何性能压测**，因此不给出任何吞吐/延迟数值。

## 21.1 已确认问题

### PERF-00｜Redis 不可用时上报接口无限阻塞（**严重，已实测 —— 已修复 2026-09-16**）

> **修复状态**：已修复。`tasks/__init__.py` 设 `task_ignore_result=True` + broker/backend 短超时与有限重试；`services/logs.py:create_log` 用 try/except 兜底。修复后实测：无 Redis 时 `.delay()` **4.06s** 抛 `OperationalError`，`POST /api/logs` 稳定返回 **201**（日志已落库，由 Beat 兜底补检）。回归用例：`tests/test_resilience.py`。下文原分析保留作为背景。

| 项 | 内容 |
|---|---|
| 位置 | `services/logs.py:57-58`（请求线程内 `.delay()`）+ `tasks/__init__.py:6-7`（Redis 兼作 result backend） |
| 证据 | 实测栈：`celery/app/task.py:444` → `app/base.py:798 send_task` → `celery/backends/redis.py:373 on_task_call` → `_reconnect_pubsub` → `retry_over_time` → `redis/connection.py:615 _connect`；`pytest tests/test_detection.py` 与全量 `pytest` 均 **>300s 未返回** |
| 机理 | 发布任务时 Celery 的 Redis **结果后端**会启动 pubsub 消费端（`on_task_call`），连接失败后进入无限重试循环；该调用发生在 FastAPI 请求线程（同步 `def` 端点 → 线程池）中 |
| 影响 | ① 上报接口不返回，被监控系统超时并可能重试 → 重复上报；② 线程池被占满 → **整个平台不可用**；③ 日志实际已入库，造成「调用方认为失败、系统已有数据」的不一致 |
| 建议 | ① 关闭结果后端（`task_ignore_result=True`）或改用独立 backend；② `apply_async(..., retry=False)` 并设置连接/传输超时；③ 把入队动作移出请求路径（写「待检测队列」表，由 Beat 兜底扫描）；④ 上报接口加超时与降级返回（202 + 落库成功即可） |

### PERF-01｜`GET /api/stats` 的 `days` 无上限 → 逐日查询放大（**高，源码确定**）

| 项 | 内容 |
|---|---|
| 位置 | `api/stats.py:18`（`days: int = 7` 无校验）、`:43-50`（`for i in range(days-1,-1,-1)` 每日一次 `COUNT`） |
| 证据 | 源码事实；`pytest` 实测该端点无越界用例。对照 `/api/stats/alerts` 有 `1..365` 校验（`api/stats.py:71-72`） |
| 影响 | 单次请求 `?days=N` 产生 N 次数据库往返；N=100000 时足以长时间占用连接与 CPU，构成**低成本 DoS**（仅需一个有效 JWT） |
| 建议 | 加 `Query(7, ge=1, le=365)`；把逐日循环改为**单条 `GROUP BY DATE(login_time)`** 查询后在应用侧补齐空日期 |

### PERF-02｜`GET /api/stats/alerts` 同样是逐日循环（**中，源码确定**）

`api/stats.py:82-93` 每日一次 `COUNT`，`days=365` 时为 365 次查询；另加 2 次 `GROUP BY`（`:96-105`）。虽有 365 上限，但在 `days=30`（管理端默认切换值）时也已产生 30+2 次查询。

### PERF-03｜日志列表的「计数 + 取数」两次查询（**中，源码确定**）

`services/logs.py:44-45`：先 `query.count()` 再 `offset/limit/all()`。两次查询不是同一快照，且 `count()` 在 MySQL 上为全表/索引扫描。同类模式也出现在 `api/alerts.py:36-37`。

**建议**：对深分页改游标分页（`WHERE login_time < :cursor`），或在数据量可控时接受该开销。

### PERF-04｜定时检测对每个用户 2 次聚合查询（**中，源码确定**）

| 项 | 内容 |
|---|---|
| 位置 | `tasks/detection.py:122-135`（对每个 username 调用两次检测）+ `services/detection.py:44-48`、`:111-115`（每次一条聚合查询） |
| 影响 | 若增量窗口内有 M 个活跃用户 ⇒ **2M 次查询**，且这些查询逐个串行执行 |
| 缓解因素 | 有复合索引 `idx_login_logs_username_login_time`（`versions/2026_07_10…:36-40`），单次查询代价可控 |
| 建议 | 改为单次 `GROUP BY username` 批量筛选「潜在命中用户」，再对候选者精算 |

### PERF-05｜每条告警新建 Redis 连接且不关闭（**中，源码确定**）

`tasks/detection.py:19` 在 `_publish_alert_event` 内 `redis.from_url(...)`，每次调用创建新连接池，代码中**没有 `close()`**（`:16-27`）。告警量增大时会出现大量短连接，依赖 GC 回收。**建议**：改为模块级共享客户端（Redis 客户端本身线程安全、自带连接池）。

### PERF-06｜SSE 长连接长期占用数据库连接（**中，分析结论**）

| 项 | 内容 |
|---|---|
| 位置 | `api/notifications.py:31-36` 的 `db: Session = Depends(get_db)`，而 `core/database.py:11-16` 的 `finally: db.close()` 在**流结束**时才执行 |
| 机理 | 该 DB 会话只在建流前用于校验 token（`_get_user_from_token`），但会一直持有到客户端断开 |
| 影响 | SQLAlchemy 默认 `pool_size=5, max_overflow=10`（`core/database.py:6` 未覆盖）⇒ **约 15 个并发 SSE 连接即可耗尽连接池**，随后所有数据库请求排队等待（默认 `pool_timeout=30s` 后报错） |
| 建议 | 建流前用**独立的短生命周期会话**完成校验并立即关闭；端点不再声明 `db` 依赖 |

### PERF-07｜每条 SSE 连接各建一个 Redis 连接（**低，源码确定**）

`api/notifications.py:38-40` 每个 SSE 请求 `aioredis.from_url(...)` + `pubsub()`；`finally` 中有关闭（`:56-59`），因此不构成泄漏，但连接数随在线管理端线性增长。

### PERF-08｜无任何缓存层（**中，源码确定**）

实测：全项目未引入缓存库或本地缓存逻辑。具体表现：

- 每个受保护请求都要查询一次 `users`（`core/deps.py:40`）；
- 统计接口每次实时聚合（`api/stats.py`）；
- 邮件配置状态每次读 settings（`api/settings.py:23`，本身无需缓存）。
- Redis 虽已接入，但**只用于 Celery/pub-sub/游标**，没有被用作缓存。

**建议**：统计类接口结果缓存 30–60 秒（Redis 已就绪，改造成本低）。

### PERF-09｜邮件发送为「每告警一次 SMTP 连接」（**低，源码确定**）

`tasks/email.py:83` 每次 `SMTP_SSL` 新建连接 + 登录。告警批量产生时会有连接开销，但对本项目量级影响有限。

### PERF-10｜Flutter 登录后一次性构建 4 个页面并发起请求（**中，📄**）

`flutter_app/lib/pages/shell_page.dart:287` 用 `IndexedStack` 承载 4 页 ⇒ 登录瞬间 4 页全部构建并各自 `initState` 发请求，加上 SSE 建连，短时间内并发 5–6 个请求（📄）。**建议**：改为 `PageView`/按需构建，或把首屏数据请求下沉到需要时触发。

### PERF-11｜SSE 推送触发整页重建（**低，📄**）

`flutter_app/lib/pages/shell_page.dart:63,87`：`context.watch<NotificationProvider>()` 使每次推送都重建整个 Shell 子树（Vue 侧用 Pinia 细粒度订阅，影响较小）。
