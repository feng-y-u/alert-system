## 本周完成工作

### 1. SSE 实时告警推送

之前，告警检测在 Celery 后端异步跑，但前端**完全不知道**——管理员只能手动刷新页面才能看到新告警。本周打通了后端 → 前端的实时推送通道。

**数据流：**

```
Celery 检测任务 (detection.py)
   │ 记录告警到 DB + 发送邮件
   │
   ├─ redis.publish("alerts", {alert_id, type, severity, username})
   │
   ▼
FastAPI SSE 端点 GET /api/notifications/stream?token=<jwt>
   │ pubsub.subscribe("alerts")
   │ while True: yield SSE event
   ▼
前端 EventSource (EventSource 自动断线重连)
   │ notificationStore (Pinia)
   ├─ unreadCount++ → 侧边栏角标
   └─ ElNotification 弹出 toast
```

**后端改动：**
- `app/tasks/detection.py` — 两处检测任务（实时 + 定时）生成告警后，新增 `_publish_alert_event()` 发布到 Redis pub/sub。try/except 确保发布失败不影响告警主流程
- `app/api/notifications.py` — 新增 SSE 端点，query param JWT 鉴权，同步 Redis pubsub + `StreamingResponse`
- `app/main.py` — 注册 notifications router

**前端改动：**
- `stores/notification.js` — 新增 Pinia store，管理 EventSource 连接生命周期、未读计数、toast 弹出
- `layouts/MainLayout.vue` — onMounted 建立 SSE 连接，侧边栏"告警列表"加 `el-badge` 角标
- `Alerts.vue` — 点进告警页调 `clearUnread()` 清零角标
- `vite.config.js` — `/api/notifications` 代理禁用缓冲，确保 SSE 响应流式输出

### 2. 错误处理（L1 全局 + L2 页面三态）

**L1 Axios 拦截器扩展**（`api/index.js`）：
- 原有：仅处理 401 → 跳登录
- 新增：5xx → "服务器异常，请稍后重试"、403 → "无权限访问"、429 → "请求过于频繁"、network error → "网络连接失败"
- 原则：拦截器只弹"非业务可预期"的错误，业务级 4xx（如 400 校验）留给调用方 catch 处理

**L2 各页面 loading/error/empty 三态**：

| 页面 | 之前 | 之后 |
|------|------|------|
| Dashboard | 无 loading、无错误态、无空态 | `v-loading` + 错误占位（含重试按钮）+ 各图表无数据时显示"暂无数据" |
| Alerts | 有 loading + 空态，catch 静默 | error 占位 + 重试按钮 + clearUnread |
| LoginLogs | 同 Alerts | error 占位 + 重试按钮 |

### 3. Dashboard 优化（图表组件化 + 防抖）

原 `Dashboard.vue` 601 行，4 个 ECharts 图表配置全内联、实例全手动管理。本周拆成 4 个独立组件：

| 新组件 | 图表类型 | 行数 |
|--------|---------|------|
| `LoginTrendChart.vue` | 登录趋势折线图 | ~103 |
| `AlertTrendChart.vue` | 告警趋势折线图（琥珀色） | ~83 |
| `TypeDistChart.vue` | 告警类型分布环形图 | ~52 |
| `SeverityDistChart.vue` | 严重级别分布柱状图 | ~62 |

每个图表组件接收 `data` prop，自管 ECharts 生命周期（init → setOption → dispose），`watch` prop 变化自动重渲染。

Dashboard 主体从 601 行降至 443 行（主要为统计卡片 + CSS 样式，图表逻辑已全部移出）。time range 切换加了 300ms `lodash.debounce`，避免用户快速切换时重复请求。

### 4. MySQL 端口迁移

开发环境 MySQL 端口从 3306 迁移至 8881（Hyper-V 端口保留冲突），同步更新了 `docker-compose.yml`、`backend/.env`、`backend/.env.example`、`backend/alembic.ini`。

## 技术要点

### SSE 鉴权方案选择

`EventSource` 浏览器 API 无法设置自定义 HTTP header，因此 SSE 端点不能用 Bearer Token。改用 query param `?token=<jwt>` 鉴权，在端点内用 `decode_access_token()` + DB 查询校验：

```python
@router.get("/notifications/stream")
async def stream_notifications(
    token: str = Query(...),
    db: Session = Depends(get_db),
):
    _get_user_from_token(token, db)  # 无效则 401
    # ...
    return StreamingResponse(event_generator(), media_type="text/event-stream")
```

### 同步 Redis + async generator

本周不引入 `aioredis` 新依赖。同步 `redis.Redis` + `pubsub.get_message(timeout=1.0)` 轮询，配合 `async def event_generator()` 内部 `yield`。单用户量级足够：

```python
async def event_generator():
    try:
        while True:
            message = pubsub.get_message(timeout=1.0)
            if message and message["type"] == "message":
                yield f"data: {message['data']}\n\n"
            else:
                yield f": heartbeat\n\n"  # 保活
    finally:
        pubsub.unsubscribe("alerts")
        pubsub.close()
```

### 错误态交互设计

错误占位 + 重试按钮优于单纯 toast 提示：toast 闪现后消失，用户不知是哪个页面出错；错误占位固定在数据位，用户可明确看到失败区域，点击重试恢复。

## 遇到的问题与解决

### 1. MySQL 端口冲突

**问题：** `docker-compose up` 报 `bind: An attempt was made to access a socket in a way forbidden by its access permissions`。3306、3307 均被 Hyper-V 保留端口占用。
**解决：** 迁移至 8881 端口，同步更新 `docker-compose.yml`、`.env`、`alembic.ini`、`.env.example` 四处配置。

### 2. Dashboard.vue 行数未达预期 250 行

**问题：** 计划预期拆分后 ≤ 250 行，实际为 443 行。
**分析：** 模板 + 脚本从 ~360 行降至 ~195 行（去除 ~200 行内联 ECharts + 图表生命周期管理），但 CSS 样式（统计卡片、图表区、快捷操作）自身 ~250 行，无法压缩。实际收益：601 → 443 行，26% 缩减，图表逻辑全部解耦到独立组件。

### 3. SSE 推送字段与前端 toast 信息的匹配

**问题：** SSE 推送字段（`alert_id`, `type`, `severity`, `username`）里 `type` 是英文字段值（`frequency`/`device`），前端 toast 需显示中文。
**解决：** notificationStore 维护 `typeMap` / `severityMap` 做中英文映射，未覆盖的字段直接显示原始值，保证不崩。
