## 1. 项目概述

### 1.1 一句话定义（源码可证）

> 本平台是一个**安全审计与日志分析系统**：校园业务系统通过 `POST /api/logs`（`X-API-Key` 鉴权）把登录日志上报到本平台，平台落库后经 Celery 异步检测**频率异常**与**设备异常**两类行为，命中即生成告警，并通过 **SSE 实时推送**、**邮件**、**管理端告警列表**三条路径交付给管理员处理。

## 2. 项目背景与目标

### 2.1 背景（结合系统实际形态）

校园信息系统普遍存在以下审计盲区：

1. **登录行为集中但无人实时盯守** —— 校园统一身份认证的登录日志通常只落在业务库或文件里，事后排查才翻日志；
2. **暴力破解与账号共享难以人工识别** —— 「同一账号 5 分钟内登录几十次」「同一账号 1 小时内从多台设备登录」这两类信号需要连续时间窗口计算，人工看日志无法及时发现；
3. **告警缺少闭环** —— 即便发现异常，也缺少「谁在什么时候处理了哪条告警」的留痕。

本平台把这三件事做成一条自动化链路：**采集 → 检测 → 告警 → 处理 → 留痕**。

> 说明：以上为项目**动机**层面的论述。源码中**没有**需求调研文档、没有真实校园系统的对接记录（❓ 无法确认），因此不应在答辩中声称「已与某校系统对接」。

### 2.2 项目目标与实际达成情况对照

| 目标（设计意图） | 源码实现 | 达成 |
|---|---|---|
| 接收并持久化校园系统登录日志 | `POST /api/logs` + `services/logs.create_log()` | ✅ |
| 定义并识别异常登录行为 | 频率异常 + 设备异常两条规则（`services/detection.py`） | ✅ 两条规则 |
| 异常产生告警并去重 | `should_create_alert()` + 数据库唯一索引 `uq_alerts_pending_dedup` | ✅ |
| 告警实时送达管理员 | SSE（Redis pub/sub）+ 邮件（SMTP）+ 列表轮询 | ✅（邮件需配置 SMTP） |
| 告警闭环处理 | 状态机 `pending → acknowledged → resolved` + `resolved_at` | ✅ |

### 4.2 分层规则（源码事实）

- **分层**：`api/ → schemas/（校验）→ services/（业务）→ models/（ORM）→ MySQL`；`tasks/` 是与 `api/` 并列的**异步侧支**。
- **无 DTO 转换层**：service 直接返回 ORM 对象，由 Pydantic `response_model` + `from_attributes=True` 序列化。
- **无自动路由扫描**：每个路由文件必须在 `app/main.py` 手工 `import` 并 `include_router(prefix=settings.API_V1_PREFIX)`。
- **API 前缀是 `/api`**：变量名虽为 `API_V1_PREFIX`，但取值 `"/api"`（`core/config.py:39`）——**不是** `/api/v1`。

### 4.3 前后端通信

| 项 | 事实 |
|---|---|
| 协议 | HTTP/1.1；SSE 为长连接 `text/event-stream` |
| 数据格式 | JSON（`Content-Type: application/json`） |
| 认证 | 管理员侧 `Authorization: Bearer <jwt>`；上报侧 `X-API-Key`；SSE 用 query `?token=` |
| 前端基址 | `import.meta.env.VITE_API_BASE_URL \|\| ''`（`api/index.js:5`）。**`frontend/.env` 为空文件**，开发靠 Vite 代理，无需该变量 |
| 超时 | Axios 10s；后端无请求级超时 |
| 开发代理 | `vite.config.js`：`/api/notifications` **必须排在 `/api` 之前**且 `ws:false`+`Connection: keep-alive`，否则 SSE 被普通代理吞掉 |
| 生产代理 | `frontend/nginx.conf` 同样把 `/api/notifications` 单独匹配并 `proxy_buffering off`、`proxy_read_timeout 3600s` |

### 4.4 Redis 的四类用途（排查问题时必须区分）

| 用途 | 键/频道 | 实现位置 |
|---|---|---|
| Celery broker + result backend | — | `tasks/__init__.py` |
| 告警 pub/sub（SSE 数据源） | channel `alerts` | `tasks/detection.py:_publish_alert_event()`、`api/notifications.py:ALERT_CHANNEL` |
| 登录失败限流计数 | `login_failures:<username>:<ip>` | `core/ratelimit.py` |
| 增量检测游标 | `anomaly_detection:last_check_time` | `tasks/detection.py:LAST_CHECK_KEY` |

> ⚠️ 另有 `app/core/redis.py` 定义一个 `redis_client`，**全仓无任何 import**（已实测检索），属死代码。实际 Redis 客户端在各处用 `redis.from_url()` 自建。💡 建议删除以免误认为现成依赖。

### 7.3 路由系统

`frontend/src/router/index.js`：

- `createWebHistory()`（HTML5 history 模式，需 Nginx `try_files` 兜底 —— 已在 `nginx.conf` 提供）。

- 守卫规则（`router.beforeEach`，共 3 条 + 1 条互斥）：

| 条件 | 行为 |
|---|---|
| `to.meta.requiresAuth && !token` | → `/login` |
| `to.path === '/login' && token && !mustChange` | → `/` |
| `token && mustChange && to.path !== '/change-password'` | → `/change-password`（强制改密） |

### 7.5 前端数据流（以告警列表页为例，逐跳对应代码）

```
① 用户点击侧边栏「告警列表」
     MainLayout.vue 的 <router-link :to="item.path">  →  router/index.js 守卫放行
② 视图挂载
     Alerts.vue: onMounted(() => { execute(); notificationStore.clearUnread() })
③ 取数
     useTableQuery(getAlerts, { limit: 20 })  →  fetchPage(skip, limit)  →  api/alerts.js: getAlerts(params)
④ 出网
     api/index.js 请求拦截器：从 localStorage 取 token → 注入 Authorization: Bearer <jwt>
     axios.get('/api/alerts', { params })
⑤ 网络
     开发：Vite proxy /api → localhost:8001；生产：Nginx /api → backend:8000
⑥ 后端
     api/alerts.py: list_alerts()
       Depends(get_current_active_user)  →  core/deps.py 解析 JWT、查 User、校验 is_active 与 must_change_password
       _active_alerts(db)  过滤 deleted_at IS NULL
       叠加 status / severity / username 过滤  →  count() + offset/limit  →  order_by(created_at DESC, id DESC)
     响应：{ items, total, skip, limit }
⑦ 回程
     api/index.js 响应拦截器：return response.data（直接给业务数据）
⑧ 状态落地
     useTableQuery.load()：total 越界则回退 lastValidSkip 并重新取数；否则 items.value = res.items
     →  ref 变化触发 Vue 响应式更新
⑨ 渲染
     DataTable 渲染 el-table，作用域插槽调用 StatusTag 做词条映射
     TablePagination 由 total/skip/limit 反算当前页码
⑩ 用户改状态
     handleStatusChange(id, cmd) → updateAlertStatus() → PUT /api/alerts/{id}
       （注意：store 中另有一条独立链路 —— SSE 推送 → notification.js:markUnread() → ElNotification）
```

**「组件 → Pinia」的分工**：列表数据由**组件局部 `ref`** 持有（`useTableQuery`），不进 store；**只有跨页面共享的状态**才进 Pinia —— `auth`（token/username/mustChangePassword，与 `localStorage` 双向同步）与 `notification`（SSE 连接、未读计数）。这是刻意的取舍：列表数据生命周期与页面一致，放 store 反而要处理清理。

### 7.6 SSE 实时告警前端链路

```
后端 Celery：_publish_alert_event(alert)
   → redis.publish("alerts", {"alert_id","type","severity","username"})
   → api/notifications.py 的 event_generator 读 pubsub → yield "data: {...}\n\n"
   → 浏览器 EventSource
   ↓
frontend/src/stores/notification.js
   connect(token)：
     eventSource = new EventSource(`/api/notifications/stream?token=${token}`)
     onopen  → isConnected=true, reconnectAttempts=0
     onmessage → JSON.parse → markUnread(alert_id)（按 id 幂等）→ ElNotification 弹窗
     onerror → isConnected=false, reconnectAttempts++
               超过 MAX_RECONNECT_ATTEMPTS(10) → closeSource() 彻底停止
               否则 setTimeout 退避重连（attempts*2000，上限 10000ms）
   MainLayout onMounted → connect(localStorage.token)；onUnmounted → disconnect()
   Alerts.vue onMounted → clearUnread()
   App.vue 网络恢复 → fetchLatestAlertsOnReconnect() → getAlerts({limit:10,status:'pending'}) → markUnread 幂等补数
```

> **为什么 token 走 query 参数**：浏览器 `EventSource` **无法附加自定义请求头**，因此这里绕开了统一的 Bearer 依赖，在 `api/notifications.py` 内自行 `decode_access_token`。这是有意的设计取舍，❌ 不应「统一」回 Bearer。

### 8.3 Celery 配置要点（`app/tasks/__init__.py`，57 行）

### 8.4 错误处理约定（源码实际行为）

| 场景 | 状态码 | 实现位置 |
|---|---|---|
| 未带凭证 / token 无效或过期 / 用户不存在 | 401 | `core/deps.py:get_current_user()` |
| 用户被禁用（带 token 访问接口） | **400** | `core/deps.py:get_current_active_user()` |
| 用户被禁用（登录时） | **401** | `services/auth.py:authenticate_user()` → `api/auth.py` 401 |
| 未修改初始密码 | 403 | `core/deps.py:get_current_active_user()` |
| 用户名或密码错误 | 401 | `api/auth.py:login()` |
| 登录失败次数超限 | **429** + `Retry-After` | `core/ratelimit.py` + `api/auth.py:login()` |
| 请求体 / 单参数校验失败 | 422 | FastAPI 内建 |
| `Depends(Model)` 注入的参数校验失败 | 422（经 `_validated` 转换，否则会漏成 500） | `api/logs.py:_validated()` |
| 查询时间范围反序 | 422（模型内抛 `HTTPException`） | `schemas/logs_query.py:check_time_range()` |
| 销毁类操作缺 `confirm=true` | **409** | `api/logs.py`、`api/alerts.py` 的 `_require_confirmation()` |
| 非法告警状态转换 | **409** | `api/alerts.py:ALLOWED_ALERT_TRANSITIONS` |
| 告警不存在 | 404 | `api/alerts.py` |
| SSE 订阅 Redis 失败 | **503** | `api/notifications.py` |
| 原密码错误 / 新旧密码相同 | 400 | `services/auth.py:PasswordChangeError` |
| 新密码过短 | 422（Schema）| `schemas/user.py:PasswordChange` |

> ⚠️ **状态码不一致**：「用户被禁用」在登录路径是 401、在接口路径是 400。💡 建议统一为 403（或 401）。
> ℹ️ 未定义全局异常处理器（无 `@app.exception_handler`），因此未捕获异常一律落到 FastAPI 默认 500。

### 8.5 日志

`core/config.py:configure_logging()` 使用 `logging.basicConfig(level=INFO, format="%(asctime)s %(levelname)-5s [%(name)s] %(message)s")`，输出到 stdout。关键留痕点：

| 位置 | 内容 |
|---|---|
| 启动期 | 安全警告（占位密钥）+ `effective config`（**凭据已脱敏**：`mysql+pymysql://***@host/db`） |
| 检测任务 | 实时检测完成/跳过/失败（`log_id` 与结果）、定时检测汇总、并发去重生效 |

| 认证 | 登录被限流、登录失败审计 |
| SSE | 连接建立/异常终止/关闭（含用户名） |
| 限流 | Redis 不可用时跳过检查/未记录计数/未清除计数 |

❓ 源码中未发现日志分级过滤、日志轮转（RotatingFileHandler）、结构化日志（JSON）或集中采集配置，无法确认生产日志治理方案。

复合索引：`idx_audit_logs_action_created_at (action, created_at)`。

### 10.4 表关系（真实关系，非理想化设计）

```
users ──✗── login_logs          （无外键：平台管理员 ≠ 被监控用户，二者仅"用户名"字符串层面可能同名）
login_logs ──1:N── alerts       （alerts.log_id → login_logs.id，ON DELETE SET NULL）
users ──✗── audit_logs          （audit_logs.actor_id 是裸整数，未建外键，以便保留已删除操作者的痕迹）
alerts / login_logs ──deleted_at── 软删除（数据保留，查询与统计全部排除）
```

**为什么 `alerts.username` 与 `login_logs.username` 都是裸字符串而不用外键**：被监控用户不在 `users` 表中（它们不是本平台用户），且日志可能先于任何用户记录到达。**为什么 `audit_logs.actor_id` 不建外键**：审计记录必须比被审计对象活得更久。

### 10.6 数据库访问方式

`core/database.py`（16 行）：

```python
engine = create_engine(settings.DATABASE_URL, pool_pre_ping=True)
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)
Base = declarative_base()

def get_db():
    db = SessionLocal()
    try: yield db
    finally: db.close()
```

- **同步** SQLAlchemy 2.0 ORM（`db.query(Model)` 风格）+ PyMySQL，无 async 驱动；

### 11.2 JWT 实现细节

`core/security.py`：

```python
ALGORITHM = "HS256"                                     # 硬编码，未取 settings.ALGORITHM
create_access_token(data, expires_delta=None)           # exp = now(UTC) + ACCESS_TOKEN_EXPIRE_MINUTES(默认1440)
decode_access_token(token) → dict | None                # JWTError 一律吞为 None
```

- 签发时**只放 `sub`（用户 id 字符串）+ `exp`**（`api/auth.py`：`create_access_token(data={"sub": str(user.id)})`）。
  ⚠️ 因此 **token 中不含 `role`**，无法做基于角色的判断。
- 校验时**每次从数据库重新载入 User**（`get_current_user`），所以「禁用用户即时失效」是成立的。
- ❓ **无 token 吊销机制**：改密后签发新 token，**旧 token 在过期前仍然有效**（无黑名单/版本号）。源码中未发现相关实现。
- `settings.ALGORITHM` 在 `config.py` 中定义为 `"HS256"`，但 `security.py` **未使用它**（硬编码同名常量）—— 配置改了不生效。

## 12. 异常登录检测机制（项目核心）

### 12.1 检测链路总览

异常检测有**两个入口**，复用同一套规则实现（`services/detection.py`）：

```
入口一（实时，单条）
POST /api/logs  (X-API-Key)
  └─ api/logs.py:receive_log()
       └─ services/logs.py:create_log()
            ├─ LoginLog 落库 + commit + refresh          ← 先持久化
            └─ try: detect_anomaly_for_log.delay(log.id)  ← 再投递（失败不影响上报）
                 │  except: logger.exception，由每小时 Beat 兜底补检
                 └─ tasks/detection.py:detect_anomaly_for_log(log_id)
                      ├─ detect_frequency_anomaly(db, username, log_id)   ← 以该日志的 login_time 为窗口终点
                      ├─ detect_device_anomaly(db, username, log_id)
                      ├─ 命中 → _create_alert_once() 落库
                      ├─ send_alert_email.delay(alert.id)                （未配置 SMTP 则跳过）
                      └─ _publish_alert_event(alert) → Redis PUBLISH "alerts"

入口二（定时，增量）
Celery Beat 每小时 → tasks/detection.py:run_anomaly_detection()
  ├─ last_check = Redis GET anomaly_detection:last_check_time（缺省 = now-1h）
  ├─ 取 created_at >= last_check 且未软删除日志的 DISTINCT username
  ├─ 对每个用户跑同两条规则（**不传 log_id** → 窗口终点 = datetime.now(UTC)）
  ├─ 命中 → 同样落库 + 邮件 + SSE
  └─ 全部成功后 Redis SET 游标 = now(UTC)   ← 失败时保留原游标，下轮重新覆盖该窗口
```

### 12.2 规则一：频率异常

| 项 | 内容 |
|---|---|
| 规则名称 | 频率异常（`frequency`） |
| 实现位置 | `backend/app/services/detection.py:detect_frequency_anomaly()`（第 48–116 行） |
| 触发条件 | 同一 `username` 在 **5 分钟**窗口内登录次数 **≥ 10** |
| 窗口定义 | `end_time = 当前日志的 login_time`（`log_id` 存在）或 `datetime.now(UTC)`（定时路径）；`start_time = end_time - 5 分钟` |
| 输入数据 | `login_logs` 中 `username` 匹配、`login_time ∈ [start, end]`、`deleted_at IS NULL` 的行 |
| 计数口径 | `COUNT(LoginLog.id)` —— ⚠️ **不区分 `login_status`**，成功与失败登录**一起计数**（源码 filter 中无状态条件） |
| 判断逻辑 | `if count < 10: return None` |
| 风险等级 | `10 ≤ count ≤ 30` → **medium**；`count > 30` → **high** |
| 告警文案 | medium：`用户 {username} 在5分钟内登录 {count} 次，可能存在异常`<br>high：`用户 {username} 在5分钟内登录 {count} 次，疑似暴力破解攻击` |
| 关联字段 | `log_id` 写入实时路径传入的那条日志 id；定时路径为 `NULL` |
| 触发结果 | 经 `should_create_alert()` 前置过滤 + `_create_alert_once()` 落库 → 邮件 + SSE |

### 12.3 规则二：设备异常

| 项 | 内容 |
|---|---|
| 规则名称 | 设备异常（`device`） |
| 实现位置 | `backend/app/services/detection.py:detect_device_anomaly()`（第 119–187 行） |
| 触发条件 | 同一 `username` 在 **1 小时**窗口内出现 **≥ 3 个不同的 `(user_agent, ip_address)` 组合** |
| 窗口定义 | 同规则一（5 分钟 → 1 小时） |
| 输入数据 | `SELECT DISTINCT user_agent, ip_address ...`（同一 filter 集合，排除软删除） |
| 计数口径 | `device_count = len(rows)`。⚠️ **`user_agent IS NULL` 会被当作一个独立组合**（SQL DISTINCT 中 NULL 自成一组） |
| 判断逻辑 | `if device_count < 3: return None` |
| 风险等级 | `3 <= device_count < 5`（即 3~4 个） → **medium**；`device_count >= 5` → **high** |
| 告警文案 | medium：`用户 {username} 在1小时内使用 {device_count} 个不同设备登录`<br>high：`用户 {username} 在1小时内使用 {device_count} 个不同设备登录，疑似账号共享或被盗` |
| 触发结果 | 同规则一 |

> 📌 **重要准确表述**：所谓「设备」在本项目中**精确等于 `(user_agent, ip_address)` 二元组的去重计数**，不是设备指纹、不做 UA 解析、不识别操作系统/浏览器型号。答辩时不应升级表述。

### 12.4 风险等级（真实取值）

| 级别 | 词表定义 | 产生条件（源码） | 是否会被产生 |
|---|---|---|---|
| `low` | ✅ `core/vocab.py:ALERT_SEVERITY_LOW` | ❌ **源码中无任何代码路径产生 `low`**（实测检索：`app/` 下仅 `vocab.py` 出现 `"low"`） | **不会** |
| `medium` | ✅ | frequency：10 ≤ count ≤ 30；device：3 ≤ device_count < 5 | ✅ |
| `high` | ✅ | frequency：count > 30；device：device_count >= 5 | ✅ |

> ❗ **结论**：系统实际只有 **medium / high 两个级别**。`low` 在词表、`AlertSeverity` Literal、前端 `StatusTag` 映射（`alert_severity.low = '低'`）中都存在，但**检测逻辑不会产生它**，`low` 只会由测试代码或人工直接写库出现。这是一个「词表与实现不对称」的事实。

### 12.5 告警去重（双层防护）

**第一层：应用层前置过滤** `services/detection.py:should_create_alert()`（第 190–218 行）

```
条件：同一 username + 同一 alert_type + status == 'pending'
      + created_at >= now(UTC) - 24 小时
      + deleted_at IS NULL
返回：existing is None   （True = 可以建；False = 已有未处理同类告警）
```

性质：**check-then-act，单独使用在并发下不成立**。源码注释明确写明「这里只是便宜的前置过滤」。

**第二层：数据库唯一约束（真正的不变量）**

```
生成列 pending_dedup_key = CASE WHEN status='pending' AND deleted_at IS NULL
                               THEN concat(username, '#', alert_type) ELSE NULL END
唯一索引 uq_alerts_pending_dedup (pending_dedup_key) UNIQUE
```

- 唯一索引允许多个 `NULL`，因此 `acknowledged` / `resolved` / 已软删除**都不占用去重槽位**，与既有去重语义一致；
- 写告警**必须**经 `services/detection.py:_create_alert_once()`：它把 `IntegrityError` 视为「去重生效」（回滚后返回 `None`）而不是让异常冒泡；
- 回归用例：`tests/test_detection.py::test_concurrent_detection_creates_single_alert`（双线程 `threading.Barrier` 同时检测同一用户，断言最终只有 1 条 pending 告警）。

⚠️ 绕过 `_create_alert_once()` 直接 `db.add(Alert(...))+commit()` 在并发下会抛唯一约束冲突 —— `scripts/generate_mock_data.py` 因此自行做了「每用户每类型保留最早一条」的降重（第 82–91 行）。

## 13. 告警系统设计

### 13.1 告警生成

```
异常命中（detect_*_anomaly 返回 AlertCreate）
  → should_create_alert()      24h 内同 username+alert_type 的 pending 告警是否存在
  → _create_alert_once()       db.add + commit；IntegrityError → rollback 并返回 None（去重生效）
  → db.refresh(alert)
```

字段写法（源码逐字对应）：`username` / `log_id`（实时路径有值，定时路径 `NULL`）/ `alert_type` / `alert_message`（含实际计数的中文描述）/ `severity`。`status` 由模型默认 `"pending"`，`created_at`/`updated_at` 由 `_utcnow()` 默认。

### 13.2 告警存储

存于 `alerts` 表（结构见 §10.3），软删除用 `deleted_at`。**所有读路径统一经 `api/alerts.py:_active_alerts()`**（`Alert.deleted_at.is_(None)`），统计路径用 `api/stats.py:_not_deleted()`。

### 13.3 告警查询

| 端点 | 过滤 | 排序 | 分页 |
|---|---|---|---|
| `GET /api/alerts` | `status` / `severity` / `username`，均排除软删除 | `created_at DESC, id DESC`（**id 作为 tiebreaker，避免同秒记录顺序不稳**） | `skip` + `limit`(1–100) |
| `GET /api/alerts/{id}` | 排除软删除 | — | — |
| `GET /api/audit-logs` | `action` / `actor` | `created_at DESC, id DESC` | `skip` + `limit`(≤200) |

### 13.4 告警状态机（源码精确语义）

```
ALLOWED_ALERT_TRANSITIONS = {
    pending      → {acknowledged, resolved}
    acknowledged → {pending, resolved}
    resolved     → {acknowledged}          ← 闭环终态，不能一步打回 pending
}
```

| 行为 | 结果 |
|---|---|
| 非法转换（如 `resolved → pending`） | **409**，detail 说明「`resolved` 只能转为 `acknowledged`」 |
| 同状态重复提交 | **幂等 no-op**：直接返回当前 alert，**不写库、不写审计日志** |
| 转为 `resolved` | 写 `resolved_at = now(UTC)` |
| 从 `resolved` 转出 | **保留** `resolved_at`（BUG-005 修复） |
| 从非 resolved 转出 | `resolved_at = None` |
| 每次真实变更 | 写 `audit_logs`（`alert.status.changed`，detail = `"{旧} → {新}"`） |

**为什么保留 `resolved_at`**：旧实现无条件清空，等于永久丢掉「这条告警何时被处理过」的审计事实，一次误点即不可恢复。回归用例：`tests/test_governance.py::test_resolved_at_is_preserved_when_status_moves_away`。

### 13.5 告警销毁（清空）

| 端点 | 参数 | 行为 |
|---|---|---|
| `DELETE /api/alerts` | `scope`（**必填**：`all` \| `processed`）+ `confirm=true`（**必填**） | 软删除（写 `deleted_at`）；缺 `confirm` → **409**；`processed` 只删 `acknowledged`/`resolved` |
| `DELETE /api/logs` | `confirm=true`（**必填**） | 软删除全部日志 |

**为什么是软删除而不是物理删除**：告警与日志是审计证据。软删除后立即从所有查询与统计中消失（用户体验等同删除），但数据保留可取证，且**不会触发外键冲突**。同时写入 `audit_logs`（`alerts.cleared` / `logs.cleared`，含 `affected_rows`）。

### 13.6 告警投递（三条路径）

| 路径 | 实现 | 触发时机 | 备注 |
|---|---|---|---|
| ① SSE 实时推送 | `tasks/detection.py:_publish_alert_event()` → Redis `PUBLISH alerts` → `api/notifications.py` 流式转发 | 告警落库后立即 | 载荷 `{alert_id, type, severity, username}`；发布失败只记 warning，不影响告警生成 |
| ② 邮件 | `tasks/email.py:send_alert_email(alert_id)` | 告警落库后 `delay()` 投递 | 收件人 = **所有 `role='admin'` 且 `is_active=True` 且 email 非空**的用户；使用 `smtplib.SMTP_SSL` |
| ③ 列表查询 | `GET /api/alerts` | 管理员主动查询 / 网络恢复后补拉 | `App.vue` 在 `online` 事件后调 `getAlerts({limit:10,status:'pending'})` |

**邮件默认跳过逻辑**（`is_email_configured()`）：`EMAIL_USER` 为空 → False；`EMAIL_HOST` 含 `example.com` 或 `EMAIL_USER` 含 `example` → False。跳过时只记 warning 并返回「skipped」，**不影响告警主流程**。

> ⚠️ **本项目 `backend/.env` 中 EMAIL_USER / EMAIL_HOST 是真实值（163 邮箱），因此 `is_email_configured()` 返回 True** —— 实测启动日志显示 `email_configured=yes`。即当前工作区状态下邮件链路是**启用**的。详见 §18。

### 13.7 告警处理闭环（管理员侧）

```
① SSE/通知/列表发现告警
② Alerts.vue 的「操作」下拉：标记为待处理 / 已确认 / 已处理
     → PUT /api/alerts/{id}  → 状态机校验
③ 成功后 ElMessage.success + refresh()（保留当前页与筛选）
④ 失败（如 409 非法转换）→ 直接展示后端 detail（含具体允许的转换目标）
⑤ 每次真实变更写 audit_logs
```

### 13.8 告警统计

`GET /api/stats/alerts?days=1..365`（默认 7）返回：

| Key | 计算 | 时间口径 |
|---|---|---|
| `alertTrend` | 按**业务时区自然日**分组的计数，无数据日期补 0，长度 = `days` | `created_at`；窗口 = `[business_day_start - (days-1) 天, 今日结束)` 折算为 UTC naive |
| `typeDist` | `GROUP BY alert_type`（窗口内、未软删除） | `created_at >= window_start` |
| `severityDist` | `GROUP BY severity`（同上） | 同上 |

`GET /api/stats` 另返回 `todayLogins` / `pendingAlerts` / `activeUsers` / `loginTrend`；其中 `pendingAlerts` **不做时间窗口过滤**（只按状态统计），并由 `tests/test_stats_consistency.py` 锁定为「== `GET /api/alerts?status=pending` 的 total == 库中 pending 且未软删除的告警数」。

## 14. 核心业务流程

### 14.1 管理员登录流程

```
① 前端 Login.vue：本地非空校验 → authStore.login(username, password)
② POST /api/auth/login
③ api/auth.py:login()
     a. ip = request.client.host
     b. ratelimit.is_blocked(username, ip)
          命中 → 429 + Retry-After        （Redis 不可用则 fail-open 放行）
     c. services/auth.authenticate_user(db, username, password)
          查 User → verify_password(bcrypt) → 校验 is_active
          失败 → ratelimit.register_failure() + 写 audit(auth.login.failed, detail 含 IP 与失败次数) → 401
     d. 成功 → ratelimit.reset(username, ip)
     e. 写 audit(auth.login.success, target=username, detail="来源 IP=...")
     f. token = create_access_token({"sub": str(user.id)})     exp = now + 1440min
     g. 返回 Token{access_token, token_type="bearer", must_change_password}
④ 前端 stores/auth.js:_persist()：token/username/mustChangePassword 三值同步写入 ref 与 localStorage
⑤ 路由跳转：must_change_password ? '/change-password' : '/'
⑥ 进入 MainLayout → onMounted → notificationStore.connect(token) 建立 SSE
```

### 14.2 首次登录强制改密流程

```
① 登录返回 must_change_password=true → 前端跳 /change-password，localStorage.mustChangePassword='1'
② 此时访问任何其它接口 → core/deps.py:get_current_active_user() 检测标记 → 403「请先修改初始密码」
     前端 api/index.js 拦截器识别 detail 含「初始密码」→ 再次跳 /change-password
③ 前端 ChangePassword.vue 本地校验（非空 / ≥8 位 / 两次一致 / 不同于原密码）
④ POST /api/auth/change-password（用 get_current_user，刻意绕过 403 拦截）
     services/auth.change_password()：
       verify_password(old) 失败 → 400
       len(new) < 8 → PasswordChangeError → 400      （Schema 层先返回 422）
       new == old → 400
       写入新 bcrypt 哈希 + must_change_password = False
     写 audit(auth.password.changed)
     返回**新 token**（must_change_password=false）
⑤ 前端 _persist(新token, ..., false) → 跳 /
```

### 14.3 日志上报与实时检测流程

```
① 校园系统：POST /api/logs  X-API-Key: <key>
② core/deps.py:verify_api_key()  比对 settings.API_KEY，不等 → 401
③ schemas/login_log.LoginLogCreate 校验：
     · login_time 带 offset → 折算为 UTC naive；晚于 now+5min → 422
     · login_status 归一化（success/failure；failed/fail → failure；其它 → 422）
④ services/logs.create_log()：
     db.add(LoginLog) + commit + refresh      ← 先落库
     try: detect_anomaly_for_log.delay(log.id)
     except: logger.exception（**不影响上报返回**，由每小时 Beat 兜底）
⑤ 返回 LoginLogResponse，HTTP 201
⑥ Celery Worker 消费 detect_anomaly_for_log(log_id)：
     db 中查该 log（不存在 → 记 warning 并返回）
     detect_frequency_anomaly(db, username, log_id)
     detect_device_anomaly(db, username, log_id)
     命中 → _create_alert_once() → _dispatch_alert_side_effects(alert)
              ├─ send_alert_email.delay(alert.id)
              └─ _publish_alert_event(alert) → Redis PUBLISH "alerts"
     异常 → logger.exception + self.retry（max_retries=3, delay=10s）
```

### 14.4 定时增量补检流程

```
① Celery Beat 每 3600s → run_anomaly_detection()
② last_check_time = Redis GET anomaly_detection:last_check_time
     缺省（键不存在）→ datetime.now(UTC) - 1h
③ SELECT DISTINCT username FROM login_logs
     WHERE created_at >= last_check_time AND deleted_at IS NULL
④ 对每个 username：跑频率检测 + 设备检测（**不传 log_id** → 窗口终点 = now(UTC)）
     命中 → 同样落库 + 邮件 + SSE，累计 total_alerts
⑤ 全部成功后 Redis SET 游标 = now(UTC)
     任一步抛异常 → logger.exception + self.retry（max_retries=2, delay=60s），
                     **游标保持不变**，下一轮重新覆盖该窗口（避免永久漏检）
⑥ 返回汇总字符串："Anomaly detection completed. Checked N users, created M alerts."
```

### 14.5 告警处理流程

```
① 管理员打开 /alerts → onMounted → execute() 取列表 + clearUnread()
② 或在任意页面收到 SSE → 顶部 ElNotification 弹窗 + 侧边栏「告警列表」未读徽标 +1
③ 点击行「操作」下拉 → 选择目标状态
④ PUT /api/alerts/{id} {status}
     _active_alerts 查（不存在 → 404）
     status == 当前值 → 幂等返回（不写库不写审计）
     status ∉ ALLOWED_ALERT_TRANSITIONS[当前] → 409
     resolved → 写 resolved_at；离开 resolved 时保留
     commit + 写 audit(alert.status.changed, detail="{旧} → {新}")
⑤ 前端成功 → ElMessage.success + refresh()（保留筛选与页码）；失败 → 展示后端 detail
```

### 14.6 数据统计流程

```
① Dashboard.vue onMounted → useAsyncData(immediate:true) → loadDashboard()
     并发：api.get('/api/stats', {days}) + getAlertStats(days)
     loadToken 序号守卫：过期响应（先发后到）被丢弃，不覆盖新数据
② GET /api/stats?days=N
     today_start_utc = business_day_start_utc_naive()      ← 按 BUSINESS_TIMEZONE 切自然日
     todayLogins   = COUNT(login_logs WHERE login_time >= today_start_utc AND deleted_at IS NULL)
     pendingAlerts = COUNT(alerts WHERE status='pending' AND deleted_at IS NULL)
     activeUsers   = COUNT(DISTINCT username WHERE login_time >= today_start_utc ...)
     loginTrend    = _build_trend(登录日志, days)
③ _build_trend：**单条 GROUP BY 查询**取回分组计数，再按业务自然日补 0 生成定长序列
     （SQL 侧日期折算见 api/stats.py:_business_date_expr：SQLite 与 MySQL 分支不同）
④ GET /api/stats/alerts?days=N → alertTrend / typeDist / severityDist
⑤ 前端：statCards（computed 由数据生成）→ StatCard（骨架 → useCountUp 数字滚动）
        趋势与分布 → BaseChart（首屏 sweep 入场；7/30 天切换时「淡出→原子替换→淡入」）
⑥ 切换 7 天/30 天 → watch(days, debounce(execute, 250))
```

### 14.7 清空（软删除）流程

```
① 管理员点击「清空日志」/「清空告警」
② 前端 ElMessageBox.confirm 二次确认 → 确认后 api 调用带 confirm=true 与 scope
③ 后端 _require_confirmation(confirm)：缺 confirm → 409「属于不可逆操作，需显式携带 confirm=true」
④ UPDATE ... SET deleted_at = now(UTC)（synchronize_session=False）
⑤ commit + 写 audit（affected_rows = 更新行数）
⑥ 返回 {deleted, scope?, soft_deleted: true}
⑦ 前端：skip 归零 + refresh；失败提示由拦截器统一给出（用户取消与失败已分开处理）
```

### 14.8 平台操作审计留痕流程

```
动作发生点（7 类，标识定义在 services/audit.py）
  auth.login.success     ← api/auth.py:login()
  auth.login.failed      ← api/auth.py:login()（actor=None）
  auth.user.created      ← api/auth.py:register()
  auth.password.changed  ← api/auth.py:change_own_password()
  logs.cleared           ← api/logs.py:clear_logs()
  alerts.cleared         ← api/alerts.py:clear_alerts()
  alert.status.changed   ← api/alerts.py:update_alert()
        ↓
services/audit.record(db, action, actor, target, detail, affected_rows, commit=True)
   · detail 截断到 500 字符
   · 写入失败**只记日志不抛出**（不影响业务操作）；失败时尝试 rollback
        ↓
GET /api/audit-logs（Bearer JWT，只读，支持 action/actor 过滤 + 分页）
        ↓
⚠️ 前端无审计日志页面（未调用该接口）
```

## 18. 安全分析

### 18.1 🔴 高风险发现

#### SEC-01：`backend/.env` 中存在**真实可用的 SMTP 凭据**

| 项 | 内容 |
|---|---|
| **风险** | 真实的 163 邮箱 SMTP 账号与授权码以**明文**保存在工作区文件中。任何能读到该文件的人（含打包上交、截图、备份、镜像层）都可使用该邮箱发信，并可能关联到个人邮箱的其它权限 |
| **位置** | `backend/.env` 第 5–8 行：`EMAIL_HOST=smtp.163.com`、`EMAIL_PORT=465`、`EMAIL_USER=<REDACTED>@163.com`、`EMAIL_PASSWORD=<REDACTED>` |
| **原因** | 为打通邮件告警链路填入真实凭据；`.env` 虽被 `.gitignore` 忽略（**未进入 Git 历史**），但仍是磁盘明文 |
| **加剧因素** | `docker-compose.yml` 中 SMTP 相关项已是占位值（历史提交 `6949377` 专门做了这个替换），说明团队已意识到风险，但 `backend/.env` 未同步处理 |
| **建议** | ① 立即在邮箱服务商处**吊销并重置**该授权码；② 生产改用密钥管理服务或注入式环境变量；③ 归档/上交流程中排除 `.env`（`.gitignore` 已覆盖，但人工打包时需注意）；④ 若该邮箱曾用于其它服务，一并检查 |

> 本文档对该凭据统一以 `<REDACTED>` 表示，不记录真实值。

#### SEC-02：CORS 配置为 `allow_origins=["*"]` + `allow_credentials=True`

| 项 | 内容 |
|---|---|
| **风险** | 允许任意站点携带凭据跨域调用 API。浏览器规范禁止 `*` 与 credentials 组合，Starlette 在 `allow_credentials=True` 时会把 `Access-Control-Allow-Origin` **回显为请求方 Origin**，等价于对任意来源开放 |
| **位置** | `backend/app/main.py` 第 35–41 行 |
| **原因** | 开发期图方便，未按环境区分 |
| **建议** | 按环境白名单化：`allow_origins=[settings.FRONTEND_ORIGIN]`，并新增该配置项 |

#### SEC-03：数据库弱口令贯穿多处配置

| 项 | 内容 |
|---|---|
| **风险** | `campus_user` 的库口令为极弱的 8 位字典口令，且 root 口令与之相同 |
| **位置** | `docker-compose.yml`（mysql 的 `MYSQL_ROOT_PASSWORD`/`MYSQL_PASSWORD`、backend/worker/beat 的 `DATABASE_URL`）、`backend/docker-entrypoint.sh`（第 5 行 python 内联连接串）、`backend/alembic.ini` 第 3 行静态 `sqlalchemy.url`、`backend/app/core/config.py` 第 46 行默认值、`backend/.env`、两份 `.env.example` |
| **原因** | 本地开发便利；`alembic.ini` 保留静态值作为回退 |
| **加剧因素** | 启动期安全自检 `SENSITIVE_KEYS` **只含 `SECRET_KEY` 与 `API_KEY`**，库口令即使是占位值也不会被拦截 |
| **建议** | ① 生产改为强随机口令并通过环境注入；② 把 `DATABASE_URL`、`EMAIL_PASSWORD` 纳入 `SENSITIVE_KEYS` 检查；③ 从 `alembic.ini` 移除静态凭据（`env.py` 已用 `settings.DATABASE_URL` 覆盖，该行仅作回退） |

### 18.2 🟠 中风险发现

#### SEC-04：无法吊销已签发的 JWT

| 项 | 内容 |
|---|---|
| **风险** | 改密/禁用后，**旧 token 在 24 小时有效期内仍然可用**（改密返回新 token，但不失效旧的）。用户被禁用可即时生效（每次请求查库校验 `is_active`），但改密不能 |
| **位置** | `core/security.py:create_access_token()`（载荷仅 `sub`+`exp`）；全仓无 token 黑名单/版本号/jti |
| **建议** | 引入 `users.token_version`（或 `password_changed_at`）参与校验：签发时写入，`get_current_user` 比对；或缩短有效期 + 引入 refresh token |

#### SEC-05：`X-API-Key` 校验使用非常量时间比较，且默认值是公开占位值

| 项 | 内容 |
|---|---|
| **风险** | ① `x_api_key != settings.API_KEY` 是短路字符串比较，理论上可被计时侧信道探测；② 默认值 `dev-api-key-change-in-production` 是**公开可猜**的，若部署时忘记覆盖，任何人都能向平台注入伪造日志（进而触发虚假告警、污染统计） |
| **位置** | `core/deps.py:verify_api_key()`、`core/config.py:52` |
| **缓解** | 启动期自检会检测该占位值：production 下**拒绝启动**、开发下 WARNING —— 这已显著降低风险 |
| **建议** | 改用 `hmac.compare_digest()`；对 `/api/logs` 增加速率限制与来源 IP 白名单 |

#### SEC-06：SSE 的 JWT 通过 URL query 传递

| 项 | 内容 |
|---|---|
| **风险** | token 会出现在浏览器历史、Referer、以及反向代理/Nginx 的 access log 中 |
| **位置** | `api/notifications.py`（`token: str = Query(...)`）、`frontend/src/stores/notification.js`（`new EventSource(\`...?token=${token}\`)`） |
| **原因** | **`EventSource` 无法设置自定义请求头**，这是浏览器限制下的合理取舍 |
| **建议** | ① Nginx 对 `/api/notifications` 关闭或脱敏 access log；② 改用 `fetch` + `ReadableStream` 自行实现 SSE 以便携带 Authorization 头；③ 为 SSE 单独签发**短时效、单一用途**的 token |

#### SEC-07：JWT 存储于 `localStorage`

| 项 | 内容 |
|---|---|
| **风险** | 任何 XSS 都能读取 `localStorage.token` 并冒用管理员会话 |
| **位置** | `frontend/src/stores/auth.js`、`api/index.js`（请求拦截器读 `localStorage`） |
| **缓解（已存在）** | Vue 模板默认转义；表格中 UA 与告警内容走 `el-tooltip` 的 `:content` 绑定而非 `v-html`；**实测检索确认 `frontend/src` 全仓无 `v-html` / `innerHTML` / `eval(` / `dangerously*` 用法** |
| **建议** | 改用 `HttpOnly` + `Secure` + `SameSite=Strict` Cookie 承载 token（同时需引入 CSRF 防护） |

#### SEC-08：`monitored-app` 的安全缺陷（独立组件，但会进镜像/仓库）

| 项 | 内容 |
|---|---|
| **风险** | ① `app.run(..., debug=True)` → Werkzeug 调试器，若暴露可导致任意代码执行；② `app.secret_key = "monitored-app-dev-key"` 硬编码；③ 用户口令用**无盐 SHA-256** 存储（非 bcrypt），且直接可彩虹表破解；④ API Key 由**页面表单**传入并默认填入占位值，会出现在 HTML 源码中 |
| **位置** | `monitored-app/app.py` 第 10、39、54–55、95、138 行 |
| **建议** | 明确标注「仅供本地演示、禁止联网部署」；关闭 debug；改用 bcrypt；Key 从环境变量读取 |

## 19. 性能分析

> **重要前置声明**：**当前项目源码中未发现完整的性能基准测试，因此不能给出未经验证的 QPS、响应时间等具体指标。** 本节仅从代码与架构角度做**定性分析**，并给出**实测到的构建产物体积**等可复核数据。

### 19.1 数据库查询与索引

| 查询场景 | 涉及查询 | 索引利用 |
|---|---|---|
| 频率检测（实时） | ① 取当前日志 ② `COUNT` 时间窗口内记录 | ② 命中 `idx_login_logs_username_login_time (username, login_time)` ✅ |
| 设备检测 | ① 取当前日志 ② `SELECT DISTINCT user_agent, ip_address`（时间窗口） | 同上，但需回表取 `user_agent`/`ip_address`，非覆盖索引 |
| 去重检查 | `SELECT ... WHERE username=? AND alert_type=? AND status=? AND created_at>=? AND deleted_at IS NULL` | 前缀命中 `idx_alerts_username_alert_type_status` ✅（`created_at` 与 `deleted_at` 走过滤） |
| 日志列表 | `COUNT` + `SELECT ... ORDER BY login_time DESC LIMIT/OFFSET` | 排序走 `login_time`；⚠️ 无 `login_time` 单列索引，见下 |
| 仪表盘今日统计 | `WHERE login_time >= today_start AND deleted_at IS NULL` 的 3 个聚合 | ⚠️ **无 username 条件**，无法使用以 `username` 为前导列的复合索引 → 可能全表扫描 |
| 告警统计 | `WHERE created_at >= window_start GROUP BY alert_type/severity` | ⚠️ `alerts.created_at` **无索引** → 可能全表扫描 |
| 审计日志 | `WHERE action=? ORDER BY created_at DESC` | 命中 `idx_audit_logs_action_created_at` ✅；`created_at` 另有单列索引 ✅（支持仅按时间排序） |

**索引缺口小结（💡 建议）**：

| 建议新增 | 理由 |
|---|---|
| `login_logs(login_time)` | 仪表盘「今日登录」「活跃用户」与趋势统计均只按 `login_time` 过滤；当前复合索引前导列是 `username`，用不上 |
| `alerts(created_at)` | 告警趋势/类型分布/级别分布全部按 `created_at >= window_start` 过滤 |
| `login_logs(created_at)` | 定时增量检测按 `created_at >= last_check` 过滤 |
| 覆盖索引 `login_logs(username, login_time, user_agent, ip_address)` | 设备检测的 `DISTINCT` 可免回表（代价是索引体积与写放大） |

### 19.2 已做的查询优化（源码可证）

| 优化 | 位置 | 说明 |
|---|---|---|
| 趋势统计从「逐日 N 次 COUNT」改为**单条 GROUP BY** | `api/stats.py:_daily_counts()` / `_build_trend()` | 源码注释明确标注（P1-1）。`days=365` 时由 365 次查询降为 1 次 |
| 为 `days` 增加范围校验（1–365） | `api/stats.py:DAYS_MIN/DAYS_MAX` + `Query(ge=, le=)` | 消除 `?days=100000` 造成的资源耗尽面 |
| 分页上限 | `/api/logs`、`/api/alerts` `limit ≤ 100`；审计 `≤ 200` | 防止单次拉取过大 |
| `pool_pre_ping=True` | `core/database.py` | 避免取到 MySQL 已断开的连接 |
| 软删除用 `UPDATE ... synchronize_session=False` | `api/logs.py`、`api/alerts.py` | 批量更新不做 ORM 对象同步 |
| SSE 使用独立短会话 | `api/notifications.py` | 不再为长连接持有请求级 DB 会话（否则约 15 个并发连接即可耗尽默认连接池） |
| Celery `task_ignore_result=True` + 短超时 | `tasks/__init__.py` | 消除 Redis 不可用时上报请求被 pubsub 消费端无限重连卡死的问题 |
| 排序加 `id` 作为 tiebreaker | `api/alerts.py`、`api/audit.py` | 避免同秒记录分页顺序不稳 |
| 检测查询排除软删除 | `services/detection.py` 各处 `.filter(LoginLog.deleted_at.is_(None))` | 语义正确性 + 减少扫描量 |

### 19.3 架构层面的性能特征

| 项 | 现状 | 影响 |
|---|---|---|
| DB 驱动 | **同步** SQLAlchemy + PyMySQL | FastAPI 的同步 `def` 端点在线程池中执行，默认 40 线程；高并发下线程池是瓶颈 |
| 缓存 | 仅 Redis 用于队列/限流/游标/pubsub，**无查询结果缓存** | 仪表盘每次刷新都打 DB |
| 分页 | `OFFSET/LIMIT` | 深分页（`skip` 很大）性能线性退化；本项目 `limit ≤ 100`，实际影响有限 |
| 检测触发 | 每条日志投递一次任务，任务内**每条 2 次查询 + 可能 1 次 INSERT** | 上报量大时 Worker 队列会积压；定时 Beat 为**兜底**而非主路径 |
| 定时检测 | 对增量用户**串行**逐个跑两条规则 | 用户数大时单轮耗时线性增长（当前无并发/分批） |
| 日志高频写 | 每条上报一次 INSERT + 一次 commit | 无批量写入 |
| 事务粒度 | 每个请求一次或数次 commit | `_create_alert_once()` 中 `IntegrityError` 会触发回滚 |
| 邮件/通知 | Celery 异步 | ✅ 不阻塞上报 |
| 时区折算 | 在 **SQL 侧**做（`date_add` / `date`） | ✅ 避免把全量数据拉到应用层；但表达式上**无法用索引**，趋势统计在大表上是全扫 |

## 23. 实习答辩重点

### 23.1 项目一句话介绍（开场用）

> 「我做的是一套**校园账号异常登录监测与告警平台**。它不面向师生，而是给安全管理员用的运维监控系统：校园业务系统把登录日志通过 API Key 上报进来，平台用 Celery 异步检测**频率异常**（5 分钟内同一账号登录 ≥10 次）和**设备异常**（1 小时内同一账号出现 ≥3 个不同的 IP+UA 组合），命中就生成告警，通过 **SSE 实时推送**、**邮件**和**告警列表**三条路径交付，管理员处理告警后全程写入审计日志。技术栈是 FastAPI + SQLAlchemy + MySQL + Celery + Redis，前端 Vue 3 + Element Plus + ECharts，119 个自动化测试全部通过。」

### 23.2 项目背景（为什么需要它）

校园统一身份认证每天都产生大量登录记录，但**没人实时盯**。两类风险人工看不出来：一是暴力破解（短时间高频登录），二是账号共享或被盗（短时间多设备登录）—— 它们都需要**滚动时间窗口的计数**才能识别。本平台把「采集 → 检测 → 告警 → 处理 → 留痕」做成一条自动化链路。

> ⚠️ 表述纪律：不要说「已与某校系统对接」「某校在用」。源码中没有真实对接记录，`monitored-app/` 是**仿真上报端**。

### 23.3 项目目标（与实际实现逐条对应）

| 目标 | 实现 |
|---|---|
| 日志采集与持久化 | `POST /api/logs`，`X-API-Key` 鉴权，入库即归一化时间与状态词表 |

### 23.4 核心功能（适合直接做成 PPT 列表）

1. **管理员认证与强制改密** —— JWT（HS256）+ bcrypt；初始口令首次登录必须修改，否则除改密外一律 403
2. **登录失败限流** —— 同一「用户名+IP」15 分钟内失败 5 次即 429；Redis 故障自动放行并熔断 30 秒
3. **登录日志采集** —— API Key 鉴权；时间与状态词表入库即归一化；拒绝超前 >5 分钟的未来时间
4. **日志检索与审计** —— 用户名模糊（`%`/`_` 已转义）、IP 精确、状态、日期范围（按业务时区折算）、分页
5. **异常检测（核心）** —— 频率异常（5min / ≥10 次，10–30 → 中，>30 → 高）+ 设备异常（1h / ≥3 个 IP+UA 组合，3~4 → 中，≥5 → 高）
6. **告警去重（双层）** —— 24h 前置过滤 + 生成列唯一索引；并发下保证同一用户同类型只有一条待处理告警
7. **实时告警推送** —— Redis pub/sub → SSE；前端未读徽标幂等计数、10 次重连上限、断网恢复幂等补拉
8. **邮件告警** —— 异步发送给全部启用中的管理员；未配置 SMTP 自动跳过，不影响主流程
9. **告警闭环处理** —— `pending → acknowledged → resolved` 状态机，非法转换 409，同状态幂等，`resolved_at` 保留
10. **软删除销毁** —— 清空需 `confirm=true`，只写 `deleted_at`（保留取证），并写审计
11. **仪表盘可视化** —— 今日登录 / 待处理告警 / 活跃用户 + 登录趋势 + 告警趋势 + 类型分布 + 级别分布
12. **平台自身审计** —— 登录成功/失败、创建管理员、改密、清空日志/告警、告警状态变更

### 23.6 核心创新 / 技术特点（**只写源码能证明的**）

> ⚠️ 不要造「创新点」。以下是可直接用代码证明的工程亮点，定位为**技术特点**而非学术创新。

1. **把并发去重下沉到数据库**：`alerts` 表用生成列 `pending_dedup_key`（`status='pending' AND deleted_at IS NULL` 时取 `username#alert_type`，否则 `NULL`）+ 唯一索引。多个 `NULL` 不冲突，因此 `acknowledged`/`resolved`/软删除都不占用去重槽位，与业务语义精确对齐。应用层把 `IntegrityError` 视为「去重生效」而非错误。**用双线程 barrier 的回归测试证明修复前会稳定产生 2 条重复告警。**
   - 加分细节：生成列表达式用 SQLAlchemy `concat()` 而非 `text("CONCAT(...)")`，因为前者在 MySQL 编译为 `concat()`、SQLite 编译为 `||`，**单一定义同时适配生产库与测试库**；而 SQLite 的 `ALTER TABLE` 不支持新增 STORED 生成列，这一点在迁移注释中被专门记录。
2. **「先落库再投递」的上报语义**：`create_log()` 先 commit，再 try/except 投递检测任务。Redis 故障时上报仍返回 201 且日志已持久化，由每小时 Beat 的增量扫描兜底补检 —— 这是一次真实事故（result backend 的 pubsub 消费端无限重连把请求线程卡死 >300s）之后的修复，配合 `task_ignore_result=True` + 短超时 + 有限重试，实测快速失败。
3. **时间口径的端到端统一**：库内一律 UTC naive；对外自然日按 `BUSINESS_TIMEZONE`（默认 Asia/Shanghai）切分；Celery 用同一时区；SQL 侧日期折算按方言分支（SQLite `date(col, "+N hours")` / MySQL `date_add(col, INTERVAL N HOUR)`）；入口处把带 offset 的入参统一折算（因为 **MySQL 对 aware datetime 会静默剥离 tzinfo**，不折算就整体差 8 小时）。
4. **把「参数校验失败必须是 4xx」当成硬约束**：FastAPI 只对请求体和单参数把校验错误转 422，而 `Depends(PydanticModel)` 注入的校验错误会穿透成 **500**。项目用 `_validated()` 统一收口，并用 13 个参数化用例把「6 个非法参数 → 422 / 7 个合法参数 → 200」钉死。
5. **限流 fail-open + 熔断**：Redis 不可用时登录放行（避免把管理员锁在门外），并用 30 秒熔断避免每次登录都付连接超时；有专门的回归用例断言「熔断期内不再尝试连接 Redis」。
6. **软删除保护审计证据**：清空接口只写 `deleted_at`，数据立即从所有查询与统计中消失但保留取证可能，并写审计日志（含 `affected_rows`），同时避免外键冲突。
7. **词表收敛为唯一事实来源**：`core/vocab.py` 集中定义 `login_status`/`alert_type`/`severity`/`status` 与密码最小长度，写入侧用 Pydantic `Literal` 校验（422），并把历史别名 `failed`/`fail` 在**入库时**归一化为 `failure`（历史 Bug：「数据能入库但按失败筛不出来」）；数据库侧另有迁移做存量归一化。
8. **前端不是「能跑就行」**：存在一整套被显式设计过的交互细节 —— 请求序号守卫（丢弃过期响应）、防抖、失败重试冷却、**越界页自动回退到最后一个有效页**、图表换数据的「淡出→同帧原子替换→淡入」（不产生两套数据的中间形态，只保留最后一个 pending option）、数字滚动时长自适应、`prefers-reduced-motion` 运行时响应式降级、SSE 未读**按 id 幂等计数**（断网补拉不重复累加）与重连计数不因 `disconnect()` 归零。

### 23.7 项目难点（结合真实复杂度）

| 难点 | 为什么难 | 怎么解决的 |
|---|---|---|
| **并发告警去重** | check-then-act 在并发下必然失效；两个检测任务都会查到「没有 pending 告警」 | 下沉到数据库：生成列 + 唯一索引；`IntegrityError` 语义化为「去重生效」；双线程回归测试 |
| **Redis 故障不得放大为全站故障** | Celery 的 `.delay()` 在 broker/backend 不可用时会长时间阻塞请求线程 | `task_ignore_result=True` + 短连接超时 + 有限重试 + `create_log` 的 try/except + 每小时 Beat 兜底 |
| **时区一致性** | 数据库存 UTC naive、界面按本地自然日筛选、Celery 按时区调度、MySQL 静默剥离 tzinfo | 统一 `BUSINESS_TIMEZONE` 口径，入口折算、SQL 侧按方言折算、有 3 个回归用例锁定上海日界 |
| **FastAPI 依赖注入的错误码语义** | `Depends(PydanticModel)` 的 `ValidationError` 会变成 500 而不是 422 | `_validated()` 依赖包装器 + 参数化回归用例 |
| **SSE 的鉴权与代理穿透** | `EventSource` 不能带自定义头；Vite/Nginx 的顺序与缓冲会吞掉 SSE | query 传 token + `api/notifications.py` 自行校验；代理中 `/api/notifications` 单独匹配且置于 `/api` 之前、`proxy_buffering off` |
| **Alembic 生成列跨方言** | MySQL 需 `STORED`（否则不能建索引）；SQLite 的 `ALTER TABLE` 不支持新增 STORED 生成列；且 `alembic_version.version_num` 是 `VARCHAR(32)`，revision id 超长会导致「DDL 成功但版本号写入失败」的不一致状态 | 用 `CreateColumn(...).compile(dialect)` 按方言渲染；revision id 控制在 32 字符内 |
| **测试必须离线可跑** | 原测试依赖 Redis/MySQL 会挂死 | 临时 SQLite + autouse fixture 全局屏蔽 Celery 投递 + patch Redis |

## 24. 答辩可能提问

### 24.1 架构与设计类

**Q1：为什么选 FastAPI 而不是 Django/Flask？**
A：三个具体原因：① 项目需要**异步任务与长连接（SSE）**，FastAPI 基于 ASGI，原生支持 `StreamingResponse` 做 SSE，`api/notifications.py` 直接返回 `StreamingResponse(event_stream, media_type="text/event-stream")`；② 自动生成 OpenAPI 文档（`/docs`），对「被外部系统调用的上报接口」很关键；③ 依赖注入（`Depends`）天然适合做**多套鉴权**——本项目同时有 Bearer JWT、`X-API-Key`、以及 SSE 的 query token 三种入口，用依赖组合很清晰。
（补充诚实说明：Django 的 admin 和 ORM 也够用，选型也受个人熟悉度影响。）

**Q2：为什么用 Celery？检测不能同步做吗？**
A：不能。实时检测要对同一用户做**两次聚合查询**（5 分钟计数 + 1 小时 DISTINCT），而且上报接口是校园系统调用的、对延迟敏感。同步做会让上报接口的响应时间取决于检测耗时和数据量。用 Celery 后 `POST /api/logs` 只做一次 INSERT + 一次任务投递。
**但这里有个重要的工程细节**：投递本身也可能被 Redis 拖住，所以我们做了「先落库、再投递、投递失败只记日志」，并且有一层每小时 Beat 的增量扫描兜底 —— 保证「上报不因队列故障而丢」。

**Q3：为什么要两个检测入口（实时 + 定时）？**
A：职责不同。实时入口保证**及时性**（日志到达即检测）；定时入口保证**完整性**（Redis 故障期间的日志、以及历史补偿）。而且定时入口是**增量**的：用 Redis 存游标 `anomaly_detection:last_check_time`，只处理上次检测后新增日志所属的用户。关键是**游标只在全部处理成功后才推进** —— 失败时保留原值，下一轮重新覆盖该窗口，避免「先推进游标 + 异常」造成永久漏检。

**Q4：前后端怎么通信的？SSE 和 WebSocket 为什么选 SSE？**
A：REST + JSON；实时推送用 SSE。选 SSE 的理由：告警推送是**单向**的（服务端→浏览器），SSE 用原生 `EventSource` 就能实现，浏览器自动重连，且走普通 HTTP 不需要协议升级。代价是 `EventSource` **无法设置自定义请求头**，所以 SSE 的鉴权只能用 query 参数传 token（`/api/notifications/stream?token=<jwt>`）—— 这是有意的取舍，不是疏忽。

### 24.2 异常检测类（重点，必被追问）

**Q5：什么情况下会被判定为异常登录？**
A：两条规则，都是固定时间窗口的阈值判断：
① **频率异常**：同一用户名在 5 分钟内登录次数 ≥ 10 次。10–30 次记为 medium，超过 30 次记为 high。
② **设备异常**：同一用户名在 1 小时内出现 ≥ 3 个不同的 `(user_agent, ip_address)` 组合。3~4 个记为 medium，5 个及以上记为 high。
需要注意的是，**频率规则统计的是登录次数，不区分成功与失败**（源码里的 filter 没有状态条件）。

**Q6：风险等级有哪几级？分别怎么产生？**
A：词表定义了 `low`/`medium`/`high` 三级，但**实际检测只会产生 medium 和 high** —— `low` 在 `core/vocab.py` 和前端的 `StatusTag` 映射里都有，但 `app/` 下没有任何代码路径产生它。
产生规则：频率 10–30 → medium，>30 → high；设备 3~4 个 → medium，≥5 个 → high。
（⚠️ **这是一个可以主动坦白并加分的点**：「low 目前是占位词表项，如果要做时间段规则或 IP 归属地规则，low 就能派上用场。」）

**Q7：为什么阈值是 10 次 / 5 分钟？有数据支撑吗？**
A：**没有统计数据支撑，这是拍定的经验阈值。** 源码中就是硬编码的 `if count < 10: return None` 和 `timedelta(minutes=5)`。
💡 正确做法是：先用 `scripts/seed_logs.py` 造一批正常数据（200 条、13 个用户、80% 成功），统计每个用户 5 分钟窗口内登录次数的分布，再按分位数（如 P99）定阈值。这可以作为后续改进项。
（⚠️ 不要编造「基于某某论文/标准」。）

**Q8：如果攻击者改成每 6 分钟登录 9 次怎么办？**
A：能绕过。**本项目是固定窗口阈值规则，对低速慢速攻击（low-and-slow）无效** —— 这是设计上的已知局限。
缓解思路（改进方向）：① 用滑动窗口而非固定窗口；② 增加「用户日/周登录基线」的偏差检测；③ 结合失败率（攻击者通常失败率高，但本项目的频率规则把成功和失败合并计数，这是个可以改进的点）。

**Q9：`(user_agent, ip_address)` 组合能代表「设备」吗？**
A：**不能精确代表**，我在文档里也明确写了这一点。它就是「UA 字符串 + IP 的二元组去重计数」——不做 UA 解析、不做设备指纹哈希、不识别操作系统型号。
具体局限：同一台电脑换浏览器会算 2 个设备；同一手机切换 WiFi/4G 也会算 2 个设备。反过来，攻击者伪造 UA 能伪装成同一设备。
改进方向：引入规范化 UA 解析（提取 OS/浏览器族）+ 设备指纹（屏幕分辨率、时区、字体等特征哈希）。**另外还有一个细节问题**：`user_agent` 为 `NULL` 时，SQL 的 `DISTINCT` 会把 `(NULL, ip)` 当作一个独立组合，所以没上报 UA 的日志也可能触发设备告警。这也是可以收紧的地方。

**Q10：`location`（地理位置）字段参与检测吗？**
A：**不参与。** 这个字段在 `login_logs` 表里有，schema 里有，前端列表也展示了，但**任何检测函数都不读取它**。`scripts/seed_logs.py` 里还专门注释了「地理位置字段已弃用」，可 `generate_mock_data.py` 又在写假地点 —— 两个脚本口径不一致。这是一个**表结构冗余 + 语义不明**的技术债，建议要么接 GeoIP 让它名副其实，要么从表和表单里删掉。

**Q11：告警为什么会重复？怎么防止的？**
A：这是本项目最有技术含量的一处。去重原本是「先 SELECT 再 INSERT」（check-then-act），两步之间没有互斥：两条并发日志各自投递一次检测任务，两个任务**都可能查到「没有 pending 告警」**，于是各插一条 —— 去重承诺失效，还会重复发邮件、重复推 SSE。
修复方式是把不变量**下沉到数据库**：新增生成列 `pending_dedup_key`，当 `status='pending' AND deleted_at IS NULL` 时取 `username#alert_type`，其余情况为 `NULL`；在这个列上建**唯一索引**。因为唯一索引允许多个 `NULL`，所以 `acknowledged`/`resolved`/已软删除都不占用去重槽位，和原本 24 小时去重语义完全一致。
应用层配合：写告警走 `_create_alert_once()`，把 `IntegrityError` 当作「去重生效」处理（回滚后返回 `None`），而不是让异常冒泡。
**验证**：`test_concurrent_detection_creates_single_alert` 用 `threading.Barrier` 让两个线程同时检测同一用户，断言最终只有 1 条 pending 告警；修复前实测稳定复现 2 条。

**Q12：两个检测入口的时间窗口终点不一样，会不会有问题？**
A：**会，这里有一个残留的口径不一致。** 传了 `log_id` 的实时路径用**那条日志自己的 `login_time`**（库内是 UTC naive）作窗口终点；定时路径用 `datetime.now(timezone.utc)`，是**带时区的 aware 时间**。
而项目其它地方都刻意统一成 naive UTC（`core/config.py:to_utc_naive()`）。虽然目前测试都通过、实际行为也没出问题，但这是**代码一致性上的隐患**，规范做法应统一为 `datetime.now(timezone.utc).replace(tzinfo=None)`。我会把它列进代码整洁性改进清单。

### 24.3 认证、权限与安全类

**Q13：系统怎么认证？为什么有两套鉴权？**
A：管理员用 JWT（HS256，载荷是 `sub`=用户 id + `exp`，默认 24 小时）；校园系统上报日志用 `X-API-Key`。两套是因为**调用方性质不同**：管理员是人类用户，需要会话和过期；上报方是一个后台服务，用长期静态密钥更合适（也更容易轮换和审计）。此外 SSE 因为 `EventSource` 的限制用 query 传 token。
补充一个重要细节：`get_current_user` **每次请求都会从数据库重新载入用户**，所以「管理员被禁用后旧 token 立即失效」是成立的。

**Q14：有几种角色？能不能做权限分级？**
A：**实际上只有一种**。`role` 字段默认 `"admin"`，`create_admin_user()` 也硬编码 `role="admin"`，而且**全仓没有任何接口依据 `role` 做授权判断** —— 唯一用到 `role` 的地方是 `tasks/email.py` 里筛告警邮件收件人。所以 `role` 目前基本是装饰性的。
要做分级的话改动量是：① `UserCreate` schema 增加 `role` 字段并校验；② 抽一个 `require_role(...)` 依赖；③ 在需要的端点上挂上；④ 前端加权限指令或路由 meta。

**Q15：密码是怎么存的？**
A：bcrypt 哈希（passlib 的 `CryptContext(schemes=["bcrypt"])`），不是明文也不是 MD5/SHA。密码策略是最小 8 位（`core/vocab.py:MIN_PASSWORD_LENGTH`，schema 和 service 用同一个常量）、最大 128 位，且新密码不能与原密码相同。
没有复杂度要求（大小写/数字/符号）、没有密码历史、没有定期过期策略。

**Q16：登录接口怎么防爆破？**
A：Redis 固定窗口计数限流：键是 `login_failures:<用户名小写>:<IP>`，失败时 `INCR` + `EXPIRE`（pipeline 原子执行），达到 `LOGIN_MAX_FAILURES`（默认 5）次即返回 **429** 并带 `Retry-After` 头；登录成功清零。
设计上有个刻意的取舍：**Redis 不可用时 fail-open 放行**，因为限流是加固手段，不该因缓存故障把管理员锁在门外。同时加了 30 秒**熔断**，避免每次都去等连接超时（超时设的是 0.5 秒）。这个行为有专门的回归用例断言「熔断期内不再尝试连接 Redis」。
局限：**只覆盖登录接口，其它端点没有限流。**

**Q17：SQL 注入怎么防的？**
A：全部走 SQLAlchemy ORM 的参数化查询，没有字符串拼接 SQL。有一个具体细节值得一提：用户名模糊搜索用的是 `.contains(username, autoescape=True)` —— `autoescape` 会把用户输入里的 `%` 和 `_` 当**字面量**处理。不加这个参数的话，搜 `_` 会被当作单字符通配符、搜 `%` 会匹配到全部记录（管理员以为在筛选，实际把全表都筛出来了）。这个 Bug 有 4 个回归用例锁定。

**Q18：有没有 CSRF 风险？**
A：当前架构下**风险较低**，因为 token 放在 `Authorization` 头（从 `localStorage` 读），不是 Cookie —— 浏览器不会自动携带，所以没有经典 CSRF 面。
但反面代价是 **XSS 风险**：任何 XSS 都能读到 `localStorage.token`。缓解措施是 Vue 模板默认转义、全仓没有用 `v-html` 渲染后端数据。
如果改成 `HttpOnly` Cookie 会更安全，但那时就**必须**同时引入 CSRF 防护。

**Q19：CORS 配置有什么问题？**
A：**有问题，而且我知道。** `main.py` 里是 `allow_origins=["*"]` + `allow_credentials=True`。浏览器规范禁止 `*` 和 credentials 组合，但 Starlette 在 `allow_credentials=True` 时会把 `Access-Control-Allow-Origin` **回显为请求方 Origin**，等价于对任意来源开放。这是开发期图方便留下的，上线前必须按环境白名单化。
同类的还有：数据库口令很弱且写在 7 个地方、`alembic.ini` 里有静态凭据、以及 `backend/.env` 里有真实的邮箱 SMTP 授权码（虽然 `.env` 已被 `.gitignore` 忽略，没进 Git 历史，但归档前应该清理并吊销）。

**Q20：JWT 用的 `SECRET_KEY` 是硬编码的吗？**
A：`config.py` 里有默认值 `your-secret-key-change-in-production`，是占位值。为此做了**启动期自检**：`assert_secure_config()` 检测 `SECRET_KEY` 和 `API_KEY` 是否含 `change-me`/`change-in-production`/`your-secret-key` 等标记片段 —— 生产环境（`ENVIRONMENT=production`）命中就**直接抛 RuntimeError 拒绝启动**，开发环境打印醒目 WARNING。这个自检在 `app/main.py` 和 `app/tasks/__init__.py` 导入时都会跑，所以 Web 进程、Celery Worker、Beat 都会检查。
**但要坦白一个不足**：`SENSITIVE_KEYS` 只包含 `SECRET_KEY` 和 `API_KEY`，**不包含 `DATABASE_URL` 里的库口令和 `EMAIL_PASSWORD`**。所以弱库口令不会被拦。这是要修的。

**Q21：改密码后旧 token 还能用吗？**
A：**能用。** 改密会签发新 token 并把 `must_change_password` 置 false，但**没有吊销机制** —— 载荷里只有 `sub` 和 `exp`，没有 jti，也没有 token 版本号或黑名单，所以旧 token 在最长 24 小时内依然有效。
改进方案：在 `users` 表加 `token_version`（或复用 `password_changed_at`），签发时写进 token，`get_current_user` 里比对 —— 版本不匹配即视为失效。这是我在文档里列的 P1 改进项。

### 24.4 数据库类

**Q22：数据库有几张表？关系是什么？**
A：4 张业务表：`users`（管理员）、`login_logs`（被监控的登录日志）、`alerts`（告警）、`audit_logs`（平台自身操作留痕），外加 Alembic 的 `alembic_version`。
关系上有两个**刻意的设计决定**：
① `login_logs.username` 和 `alerts.username` 都是**裸字符串，不建外键到 `users`** —— 因为被监控的师生**不是本平台的用户**，不在 `users` 表里，只是字符串层面的「可能同名」。
② `alerts.log_id` 是**外键**指向 `login_logs.id`，且 `ON DELETE SET NULL` —— 原来默认的 RESTRICT 会在删日志时把操作拦住；改成 SET NULL 后删日志只会解除引用，不会报错。定时检测路径产生的告警 `log_id` 本身就是 `NULL`（它不对应某一条具体日志）。
③ `audit_logs.actor_id` 也是**裸整数不建外键** —— 审计记录必须比被审计对象活得更久，管理员被删了，他的操作记录还得在。

**Q23：删除数据是真删吗？**
A：**不是，是软删除。** `login_logs` 和 `alerts` 都有 `deleted_at` 字段，清空接口只写这个标记。这样做的理由：告警和日志是**审计证据**，物理删除后就没了。软删除后数据立即从所有查询与统计中消失（管理员体验等同删除），但数据保留、可取证，而且**不会触发外键冲突**。
另外销毁类操作强制要求 `confirm=true`，缺失就返回 **409**（不是 400/422），并且写审计日志记录影响行数。
`tests/test_governance.py` 里有用例验证：清空后 `deleted_at` 非空、列表 total 归零、统计归零、审计记录存在。

**Q24：为什么测试用 SQLite 而生产用 MySQL？这样能测出问题吗？**
A：测试用临时 SQLite 是为了**离线可跑**（不依赖 Docker/MySQL，约 30 秒跑完 119 个用例）。但确实带来风险，项目里有两处专门为跨方言做了处理：
① `api/stats.py:_business_date_expr()` 按方言分支：SQLite 用 `date(col, "+N hours")`，MySQL 用 `date_add(col, INTERVAL N HOUR)`；
② `models/alert.py:pending_dedup_expression()` 用 SQLAlchemy 的 `concat()` 而不是 `text("CONCAT(...)")`，因为前者在 MySQL 编译为 `concat()`、SQLite 编译为 `||`。
还有一个**真实踩过的坑**：SQLite 的 `ALTER TABLE` **不支持新增 STORED 生成列**，只有 `CREATE TABLE` 可以 —— 所以生成列那个迁移在 SQLite 上验证时要改用 `VIRTUAL`，MySQL 侧必须 `STORED`（否则不能建索引）。
**诚实的局限**：`_business_date_expr` 的 MySQL 分支和这个 STORED 生成列，都**没有进测试套件**，只在真实 MySQL 上人工验证过。迁移脚本目前零测试覆盖，这是一个改进项。

**Q25：索引建得怎么样？**
A：有 3 个复合索引 + 若干单列索引。设计上比较到位的地方：`login_logs(username, login_time)` 正好命中检测的两个时间窗口查询；`alerts(username, alert_type, status)` 命中去重检查；`audit_logs(action, created_at)` 命中审计过滤。
**但有明确的缺口**：仪表盘统计是 `WHERE login_time >= 今日零点`（**没有 username 条件**），用不上以 `username` 为前导列的复合索引；告警统计是 `WHERE created_at >= ...`，而 `alerts.created_at` **没有索引**；定时增量检测按 `login_logs.created_at >= 游标` 过滤，也没索引。这三处在大表上会全表扫描。建议补 `login_logs(login_time)`、`alerts(created_at)`、`login_logs(created_at)`。

### 24.6 性能与部署类

**Q29：系统能支撑多大的数据量/QPS？**
A：**我不能给这个数字**，因为源码里**没有性能基准测试**，没有压测脚本、没有基准数据。给了就是编的。
我能给的是**实测到的构建数据**：前端 `npm run build` 通过（11.84 秒），主 chunk 1.10 MB（gzip 368 kB）、Dashboard chunk 1.05 MB（gzip 349 kB，主要是 ECharts 全量引入）、样式 371 kB（gzip 51 kB），Vite 对超过 500 kB 的 chunk 给出了警告。
架构层面的定性判断：同步 SQLAlchemy + PyMySQL，FastAPI 的同步端点跑在线程池里；检测是每条日志一次任务、每次任务 2 查 1 写；定时检测对增量用户串行处理；统计查询在 SQL 侧做时区折算所以用不上索引。这些都是潜在瓶颈，但**没有数据我不会给结论**。

**Q30：怎么做部署？**
A：两种方式。**Docker 一键**：`docker-compose up -d` 拉起 6 个服务（MySQL、Redis、backend、celery-worker、celery-beat、frontend），`docker-entrypoint.sh` 会先等 MySQL 就绪 → `alembic upgrade head` → `python scripts/seed.py` → 启动 uvicorn。访问 `http://localhost:8882`，默认账号 `admin/admin123`（首次登录强制改密）。
**本地开发**：`docker-compose up -d mysql redis` 只起基础设施（不要用 `up -d`，那会额外占用 8000/8882），然后后端 `alembic upgrade head` + `seed.py` + `uvicorn --port 8001`，前端 `npm run dev` 在 5173。
**要留意的端口**：MySQL 是 **8881**（非 3306）、Redis 是 **8880**（非 6379）、后端 dev 是 8001（Docker 里是 8000）。
**生产缺口**：没有 TLS（Nginx 只监听 80）、没有 Gunicorn/PM2/systemd 之类的进程管理、后端服务没有 Docker healthcheck、前端镜像需要在容器内重新构建（`dist/` 不在仓库里，改完前端要 `docker-compose up -d --build frontend`）。

**Q31：Redis 挂了系统还能用吗？**
A：能，而且这是专门设计过的。Redis 在本项目有 4 类用途，故障影响各不相同：
① **Celery broker/backend**：`POST /api/logs` **仍然返回 201**，因为 `create_log()` 是「先落库、再 try 投递」，投递失败只记日志；日志已持久化，由每小时 Beat 的增量扫描兜底补检。这块曾经出过真实事故（result backend 的 pubsub 消费端在 Redis 不可用时无限重连，把上报请求卡死超过 300 秒），修复手段是 `task_ignore_result=True` + 连接超时 2 秒 + 有限重试。
② **pub/sub（SSE 数据源）**：发布失败只记 warning，不影响告警生成；前端 SSE 会按退避重连，超过 10 次就停止并在顶栏显示「离线」。
③ **限流计数**：fail-open 放行 + 30 秒熔断。
④ **检测游标**：读不到就用「now - 1 小时」作默认回溯窗口。
有 `test_resilience.py` 两个用例专门锁定「broker 不可用时上报仍返回 201」。

### 24.7 综合与反思类

**Q32：这个项目的创新点是什么？**
A：我更愿意说**技术特点**，不硬造学术创新。真正有价值的是三处工程实现：
① **并发去重下沉到数据库**（生成列 + 唯一索引 + 把 `IntegrityError` 语义化为「去重生效」），并有双线程测试证明修复前会稳定重复；
② **上报链路的降级语义**（先落库再投递、投递失败不影响返回、每小时增量兜底），这是真实事故驱动出来的；
③ **时间口径的端到端统一**（库内 UTC naive、展示按业务时区、SQL 侧按方言折算、入口统一折算，因为 MySQL 会静默剥离 aware datetime 的 tzinfo）。
检测算法本身是**两条阈值规则**，谈不上算法创新，这一点我在文档里明确写了。

**Q33：如果重做一遍，你会改什么？**
A：按优先级说三件：
① **先定指标再写代码**：现在的阈值（10 次/5 分钟、3 个设备）是经验拍定的，正确做法是先造数统计分布再按分位数定阈值，并且把检测规则做成**可配置**而不是硬编码常量。
② **补前端页面和权限分级**：后端已经有审计查询和创建管理员的接口，但前端没页面，导致这两项能力对管理员不可见；权限只有一级，`role` 字段基本没用上。
③ **一开始就把 CI 和覆盖率建起来**：现在是 119 个用例靠人工跑，没有覆盖率数据，前端零测试，迁移零测试。前端无 lint 管线这件事也让代码风格只能靠人工 review。

**Q34：这个项目有什么已知局限？**
A（可直接背）：① 检测只有两条固定窗口阈值规则，对低速慢速攻击无效；② `low` 严重级别永远不会产生；③ 只有一级权限；④ 前端缺审计日志和管理员管理两个页面；⑤ 改密后旧 JWT 仍有效（无吊销机制）；⑥ CORS 全开、库口令弱、`backend/.env` 遗留真实 SMTP 凭据、无 TLS；⑦ 无 CI、前端无 lint、无覆盖率、前端与迁移零测试；⑧ 无性能基准数据；⑨ 频率规则把成功与失败登录合并计数，没有失败率维度；⑩ 设备异常用 `(UA, IP)` 二元组近似，不是真正的设备指纹。

**Q35：项目的核心技术难点是什么？**
A：我认为是**并发一致性**和**故障隔离**这两件事，而不是功能本身：
- 并发一致性：告警去重的 check-then-act 在并发下必然失效，必须把不变量下沉到数据库层，还要处理「唯一约束冲突算正常还是算错误」这个语义问题；
- 故障隔离：Redis 是三类功能（队列、实时推送、限流）的共同依赖，它的故障**不能放大**成上报接口不可用。这需要在 Celery 配置、请求路径、限流策略三处分别设计降级，而且每一处都要有测试兜住。
这两件事的共同点是：**功能能跑通不难，难的是在故障和并发下行为仍然正确且可预测。**
